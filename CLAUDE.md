# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Overview

Milestone is a single-file, zero-dependency HTML application — the entire app (HTML, CSS, JavaScript) lives in `milestone.html`. There is no build step and no package manager. It's a local-first project planner: a single Gantt chart with a work-breakdown hierarchy (parent/summary tasks roll up dates and progress from their children), predecessor/successor dependencies (Finish-to-Start/Start-to-Start/Finish-to-Finish/Start-to-Finish with lag), auto-scheduling (moving a task forward cascades to its dependents), and a critical-path view. The app holds several independent **plans** (each with its own tasks, backups and its own linked file — linking is mandatory, see "Mandatory file linking") behind a switcher in the top bar — see "Plans" below. It's also an installable PWA (manifest, service worker, icons), and shares the same data-durability feature set as this author's other single-file apps (Pulse, mytasks): JSON export/import, rolling local backups, deletion tombstones with undo, and File System Access API file sync (mandatory here, unlike in the other apps).

**Sibling projects**: [Pulse](../Pulse/CLAUDE.md) (a programme dashboard) and mytasks (a task manager) are this same author's other single-file apps — Milestone's PWA setup and data-durability mechanisms are ported from Pulse (see its own CLAUDE.md for the fuller narrative history behind those patterns; Milestone's own version below is the same design, freshly built rather than copy-pasted). Milestone also initially ported Pulse's switchable color-scheme system but later dropped it for a single fixed palette — see "Fixed color palette" below.

**Naming**: the app was originally called dbPlanner and renamed to Milestone — everywhere, including the source file (`milestone.html`), launcher scripts (`start-`/`stop-milestone.command`), repo and directory. The one deliberate holdover is the migration code: the persistence keys were renamed `dbplanner-v1`/`dbplanner-backups` → `milestone-v1`/`milestone-backups` and the IndexedDB database `dbplanner-fs` → `milestone-fs`, and `migrateLegacyStorage()` / `_fsMigrateLegacy()` in the script copy anything found under the old names forward on first load (copy, not move — the old entries are left as a rollback copy, and the new keys always win so a later edit is never clobbered by the stale legacy copy). Keep that code for as long as an install predating the rename might still exist; it's the only place the old names should still appear. (`milestone-v1`/`milestone-backups`/the IndexedDB `syncFile` key are also the source of the *plans* migration — see "Plans".)

## Running it

A plain `file://` open of `milestone.html` works for quick checks, but PWA install/offline support requires serving it over http — browsers refuse to register a service worker for `file://` pages. `./start-milestone.command` serves the directory on `http://127.0.0.1:8937` and opens it in Chrome/Edge (Safari can't install this kind of PWA on macOS, and the File System Access API sync feature is Chrome/Edge-only regardless of how the page is served). `./stop-milestone.command` kills the server.

**Tests** live in `tests/` (Playwright scripts that drive the real app in headless Chromium; see `tests/README.md`): `python3 tests/run_all.py` starts a static server if needed, runs every `verify_*` / `drive_*` suite three at a time plus a short seeded stress run, and exits non-zero on any failure (`--stress 100` for a long stress run, or name suites to run only those). Each suite reads the address from `MILESTONE_URL` (default `http://127.0.0.1:8937/milestone.html`). Needs `pip install playwright openpyxl` and `python3 -m playwright install chromium`. Run the whole thing before committing; when you add a feature add a `verify_<feature>.py` (copy the seeding helper from an existing one) and, if it changes what a plan may look like, an operation or invariant to `verify_stress.py`.

## Architecture

The file has three logical sections in order: CSS styles, HTML structure, and a `<script>` block containing all application logic — same convention as Pulse/mytasks.

### Data model

State lives in `localStorage`, split into the **plans** and the **device preferences**:

| key | holds |
|---|---|
| `milestone-plans` | `{ current, plans: [{ id, name, fileName }] }` — the index; `name`/`fileName` are cached copies so the switcher can list plans without loading them |
| `milestone-plan-<id>` | one plan: `{ version: 1, project: { name, updatedAt, newTaskMode: 'auto' \| 'manual', modeRev: 1, fieldNames: { text1: 'Cost centre' } }, tasks: [Task], deletedTaskIds: [{id, deletedAt}] }` — exactly `syncPayload()`, i.e. exactly what is exported, backed up and written to that plan's linked file |
| `milestone-backups-<id>` | that plan's daily snapshots |
| `milestone-prefs` | `{ theme, zoom: 'week' \| 'month' \| 'year', zoomRev, view, gridPaneWidth, gridPaneRev, showBaseline, cols, gcols }` — per-device display preferences, shared by every plan |

The prefs are deliberately kept out of `syncPayload()` and out of the plan data, matching Pulse's "personal preference stays local" convention (and so switching plans never flips your theme or zoom). IndexedDB `milestone-fs` holds one `FileSystemFileHandle` per plan under the key `'plan:' + id`.

A **task**:
```js
{
  id, name, parentId: null|id, order: Number,
  startDate: 'YYYY-MM-DD', endDate: 'YYYY-MM-DD',   // equal when milestone is true
  progress: 0-100,
  milestone: Boolean,
  color: null | 'blue'|'teal'|'purple'|'amber'|'pink'|'green'|'red'|'grey',  // null = auto (by status)
  predecessors: [{ id: taskId, type: 'FS'|'SS'|'FF'|'SF', lag: Number }],  // days, can be negative
  collapsed: Boolean,   // hierarchy expand/collapse state
  taskMode: 'manual' | 'auto',            // MS Project Task Mode — see "Task Mode" below
  startText/endText/durText: null | String, // free-text Start/Finish/Duration, manual tasks only
  // (There is no `notes` field any more — removed at the user's request. Text an older version stored under `notes` is left
  //  untouched in the data, so nothing is lost, but it is no longer shown, edited or exported, and new tasks don't get the key.)
  custom: { text1: 'x', number2: 4.5, date3: 'YYYY-MM-DD', flag4: true },   // custom fields (below); only fields that have a value are present, the object is absent when empty
  resource: String,                        // who does the work, free text ("Anna, Ben"), '' = none
  actualStart: null | 'YYYY-MM-DD',        // what really happened; recording one OVERWRITES Start (and, once finished, Finish) — see "Baselines, actual dates and variance"
  actualFinish: null | 'YYYY-MM-DD',       // (WBS, Remaining Duration, Status and the variances are *computed*, never stored — see "Task fields and columns")
  baselines: { 0: ['YYYY-MM-DD', 'YYYY-MM-DD'], 3: [...] },   // frozen [start, finish] snapshots, slots 0-10 ("Baseline", "Baseline 1"-"Baseline 10"); only leaf tasks, only what the user has set; absent when none
  updatedAt: Number      // Date.now() — last-write-wins timestamp for merge
}
```

**A task with children is a summary/rollup task**: its effective start/end/progress are computed at render time from its descendants (`effectiveDates()`, memoized per render pass) rather than stored — for an Auto summary, dragging or editing its own bar isn't supported, only its leaf descendants (a *Manually Scheduled* summary is the exception: it owns its dates — see "Task Mode"). `normalizeData()` enforces this both ways: a task that has children has its own `predecessors` forcibly cleared (a summary task can't itself be independently scheduled), and no task can pick a summary task as its predecessor (the predecessor picker in the task modal only lists leaf tasks).

### Scheduling engine

`constraintStart(task)` computes a task's earliest allowed start from its own `predecessors`, per dependency type (FS/SS/FF/SF, each with its own lag). `cascadeSchedule(changedId)` walks forward through the successor graph from `changedId`, putting each dependent task where its links say (later **or earlier**, see "Auto scheduling is bidirectional" below), and continuing on to *its* successors whenever one moved — implemented as a plain worklist/relaxation loop (not a single topological pass), since a diamond-shaped dependency graph can need a downstream task revisited after a second predecessor's own cascade lands. A *Manual* task, a task that has started and a task in a dependency cycle are skipped (a manual placement ahead of its links is surfaced by the warning triangle, never corrected).

**Auto scheduling is bidirectional (the MS Project rule — an explicit user request, built for every plan, not as a setting).** An Auto Scheduled, un-started task sits at the **earliest date its links and its constraint allow**: `placeByLinks(task)` moves it to `constraintStart(task)` when that differs from its Start — **later** when a predecessor moved out, **earlier** when one moved in, got shorter, was deleted / unlinked, or finished early (an early Actual Finish, or a start earlier than planned, now pulls Auto successors earlier). It keeps the task's working-day duration. `cascadeSchedule()` and `applyConstraints()` are both built on it. A task with **nothing to schedule against** (no usable predecessor, no constraint date → `constraintStart()` is null) keeps its dates. Before this the engine only ever pushed later (plans made then have hand-set dates and no constraints, so the first cascade that reaches such a task pulls it — deliberately no migration).
- **What keeps a date the user chose — `pinToDate(t, basis)`**: a Start typed for an Auto task (inline, in the dialog, or by dragging / resizing the bar from the left) is kept when it is a real **delay** — *later than what the task's links allow* (`constraintStart(t, false)`, links only): the task then gets **Start No Earlier Than** at that date (a typed **Finish** — or resizing from the right — gets **Finish No Earlier Than**, when it is later than the finish the task would have on its links with its current duration). Links can still push it later, never pull it before that date. **Otherwise no constraint is added** — a milestone or task that sits where its links put it, a task with no links, a date typed earlier than the links allow (the links win and the task goes to what they give) — so a constraint and its icon never appear without doing something (an earlier version pinned every typed date, as MS Project does; the user found that surprising, especially on milestones). A typed date that is *not* a delay also **drops** an existing Start/Finish No Earlier Than on that side (`ASAP`, no date: the date just typed is no longer held back by it); a *delayed* one re-points it to the new date. Only ASAP/ALAP/SNET/FNET are ever touched — an explicit MSO/MFO/SNLT/FNLT is the user's choice and is left alone — and not for manual, started, group or free-text tasks. In the dialog it applies only when the constraint fields themselves were not changed in that save. Editing the **Duration** never sets a constraint. The constraint shows as the small calendar icon by the name (tooltip: `Start No Earlier Than (21.09.2026)`). One consequence: a task dated by hand that has no constraint follows its links when one is added later (it is an ordinary ASAP task).
- **Re-placing after structural changes.** Because a task now also moves earlier, everything that changes a task's links must place the tasks it touched: inline Predecessors edit, dialog save, `deleteTaskFlow()` (and its Undo), `releaseGroup()`, and — through `linkSnapshot()` / `replanChangedLinks()` — indent and drag-move (a task that becomes a group loses its own links and every link pointing at it; the tasks that lost one are placed again) and the Undo of a clone (tasks linked to a removed copy; the copy's *current* parent may be a group that just lost its only task). `offItsLinks(t)` is the check "is this Auto task somewhere other than its links say" (used by delete-Undo to leave tasks that were already off untouched).
- Covered by `verify_pull.py` (40 checks: shorter / early-finished / deleted / unlinked predecessors, the pin on typed Start / Finish / dialog / drag, explicit constraints untouched, manual / started / linkless tasks untouched, SS and FF links, reload) and by `verify_stress.py`, whose invariant is now "an un-started Auto task with something to schedule against sits *exactly* at its `constraintStart`" (tasks that ever had an actual date are exempt), with a Gantt-drag operation.

**Leads and lags** are the same `lag` field, just signed: a positive value is a lag (delays the dependent task, e.g. "wait 2 extra days after the predecessor finishes"), a negative value is a lead (lets it start early and overlap its predecessor, e.g. "start 2 days before the predecessor finishes"). The engine never distinguished the two — `addDays(pred.endDate, 1 + lag)` and friends in `constraintStart()` already handled negative `lag` correctly from the start — but nothing in the UI ever said so, so it read as a lag-only field. The modal's lag input, the inline grid Predecessors field's placeholder, and the in-app Help panel's Dependencies section now all spell out that negative values create a lead, rather than requiring a user to already know MS Project's terminology to discover it works.

`taskCycleSet()` returns the **members** of dependency cycles — the strongly connected components (Tarjan) of more than one task, plus a task that lists itself — so the answer is exact and does not depend on the order the tasks are in (an earlier DFS version flagged every task on the search path, i.e. also tasks merely downstream of a cycle, and its answer changed with the array order, which an undo reshuffles; that made the stress test flaky). Members are excluded from `cascadeSchedule()`'s traversal and from `applyConstraints()`'s self-placement entirely and flagged with a warning icon in the grid rather than crashing or looping; a task downstream of a cycle is not a member and is scheduled by its links like any other (`verify_cycles.py`).

**Task Mode** (`task.taskMode`: `'manual'` | `'auto'`) copies MS Project's Manually Scheduled vs Auto Scheduled. Where the two behave differently:

- **Cascade**: a `'manual'` task is skipped by `cascadeSchedule()` and by `applyConstraints()`'s self-shift, so predecessors never move it — but it still keeps its dates for *its own* successors' `constraintStart()` to read. Its own constraint is ignored too (`constraintViolated()` returns false, the MSO/MFO pin in `saveTaskFromModal()` is skipped).
- **Default**: new tasks are **Auto Scheduled** (`project.newTaskMode`, changed in the **Add menu** — the arrow beside Add Task, "New tasks are" with two radio items; it lives on `project`, so it syncs; the Add Task button's tooltip names the mode). It started as Manual, like MS Project, and was changed at the user's request. Because `normalizeData()` had written `'manual'` into every project on its first save, a project without the revision marker `project.modeRev === 1` is switched to Auto **once** on load (and gets the marker) — a choice made afterwards keeps the marker and is never overridden; existing tasks keep their own modes, only the default for *new* tasks moves. Tasks with no stored `taskMode` — anything saved before Task Mode existed — normalize to Auto so old projects keep behaving as they did.
- **Switching to Auto** (`setTaskMode()` / the dialog → `rescheduleAsAuto()`): drops free-text dates and moves the task to `constraintStart()` — the earliest date its links/constraint allow, **earlier or later** than where it sat. (The ongoing cascade now pulls earlier too — see "Auto scheduling is bidirectional".) With no links there's nothing to schedule against, so dates are kept.
- **Free-text dates**: a manual task's `startText`/`endText`/`durText` (`null` = a real value; `''` = blank; otherwise arbitrary text like "TBD"). `startDate`/`endDate` always stay valid ISO placeholders so the rest of the code never sees a non-date. `isUnscheduled(t)` (manual with a text Start *or* Finish) means: no Gantt bar, ignored as a predecessor by `constraintStart()`, excluded from summary rollups (`effectiveDates()` returns `start: null`) and from `computeDateRange()`. With exactly one known date the Gantt draws a bracket (`.gantt-bracket`) at it. `normalizeData()` nulls all three for Auto tasks, and a milestone's Duration text — and its Finish text unless the milestone is **manually scheduled**: a manual milestone's **Finish can be set to text such as TBD** (an explicit user request; `startInlineEdit` and the Finish cell allow it, `commitInlineEdit` keeps the text; the Start date stays, the task is unscheduled — no bar, a bracket at the known date, ignored as a predecessor), and a real date typed into a milestone's Finish becomes the milestone's date (Start and Finish both, texts cleared, actual dates too). Its Duration stays read-only; with Start = TBD its Finish cell shows the same TBD. Covered by `verify_milestone_tbd.py`. The task dialog leaves the text alone unless the corresponding date field was actually changed (`modalOrigDates`).
- **Schedule warning**: `scheduleMismatch(t)` — a task the scheduler will *not* move (a **manual** one, or one that has **already started or finished**, see "Actual dates drive the schedule") whose links (`constraintStart(t, false)`, constraints excluded) say it can't start before a date later than its own start — a started task is judged on the day it *really* started (`actualStart`). Shown as a warning triangle in the grid (own tooltip wording for each case) and an amber outline on the bar. It only flags "starts too early"; a manual task placed *later* than its links need is not warned about.
- **Manual summary tasks**: a summary with `taskMode: 'manual'` keeps its *own* stored dates instead of rolling up (`effectiveDates()` also returns `rollStart`/`rollEnd`, drawn as a thin `.gantt-rollup` bar under it), and its Start/Finish/Duration are editable. Progress still rolls up. Note the consequence of Manual being the default: indenting a task under a Manual parent does **not** make the parent span its children until it's set to Auto.
- **Critical path** excludes manual tasks (`computeCriticalPath()`) — MS Project doesn't compute criticality for them either.

UI: its own grid column before Task Name (`.task-mode-cell`, pushpin/amber = manual, chart icon/dim = auto — the constraint indicator is a calendar icon now, so the pushpin means only one thing). Clicking it opens one shared popup (`#taskModeMenu`, `openTaskModeMenu(event, target)`; `target` is a task id — the row's Task Mode cell; the default for new tasks is chosen in the Add menu, see "The toolbar") listing the two named modes with a check on the current one; the task dialog has a matching Task Mode select. Manual bars are dashed with a paler fill, manual milestones are hollow diamonds. A manual task's inline Start/Finish editor is a text box (`inlineTextDateHtml()`, accepts `DD.MM.YYYY` or ISO via `parseUserDate()`, anything else is kept as text) with a calendar button that borrows a hidden native `<input type="date">` for its picker; `inlineBlur()` treats focus moving between the two as still editing. With the native popup open, the first Escape closes the popup and a second cancels the edit.

**`applyConstraints(taskId)` vs `cascadeSchedule(taskId)`** — two different call sites need two different things, and using the wrong one silently drops the dependency: `cascadeSchedule()` alone only pushes `taskId`'s *successors*, assuming `taskId`'s own dates just changed by an intentional, already-valid action (a drag). Saving the task modal or drag-linking a new dependency changes `taskId`'s own *predecessor list*, not its dates — `taskId` itself may now violate a constraint nothing has re-checked yet. `applyConstraints()` checks `taskId`'s own constraint first (shifting it if needed) and *then* cascades to successors; `saveTaskFromModal()` and the drag-to-link handler both call `applyConstraints()` for this reason, while the bar-drag handlers call `cascadeSchedule()` directly.

**Critical path** (`criticalPathAnalysis()`; `computeCriticalPath()` returns its `critical` set; the Gantt toolbar's route button outlines those bars and the arrows between them). The forward pass **is the schedule**: a task's early dates are the Start / Finish it has now (Auto tasks sit at the earliest their links allow, a date the user pinned is respected, a finished task's actual dates stand). A backward pass from the project's finish (the latest finish of any task) gives every task its late dates, honouring **all four link types with their lags and leads** — FS: the successor's late start minus one working day minus the lag; SS: its late start minus the lag (then the task's own duration); FF: its late finish minus the lag; SF: its late finish minus the lag (then the duration) — in **working days** (`shiftWork`, so weekends and holidays are never float). Total float = `workDiff(early finish, late finish)`, critical when it is ≤ 0 (a task already later than its late finish has negative float); `float` (a Map id → working days) is returned too. Only leaf tasks the scheduler places take part — groups, **Manual tasks** and dependency-cycle members do not (MS Project does not compute criticality for them either). A task pinned later than its links allow (SNET) is critical with the chain after it, and the tasks before it have the gap as float. Not done: completed tasks are still on the path (MS Project drops them), constraints other than the current dates are not part of the backward pass, no Total Slack column. Covered by `verify_critical.py` (27 checks: every link type with lags, pinned dates, weekends/holidays, milestones, diamonds, cycles, manual/group/finished tasks, the chart, speed) and, as properties, by `verify_stress.py`.

### Working calendar (per plan)

An explicit user request: each plan has its own working days, **Monday–Friday by default**. `project.workDays` is an array of weekdays (`0` = Sunday … `6` = Saturday); it is **absent when it is the default** (`normalizeData()` deletes it, and cleans a hand-edited value: distinct integers 0–6, nothing usable → default), so old files and old app versions are unaffected. It lives on `project`, so it is saved, exported, backed up and synced with the plan (last writer wins by `project.updatedAt`, like the plan name). Set it in **plan menu → Working calendar…** (`#calendarModalBg`, `openCalendarModal()` / `saveCalendar()`: seven toggle chips Mon–Sun and nothing else — no preset buttons (an explicit user request); at least one day required; the menu item shows the current setting, e.g. `Mon–Fri`).

**The calendar layer** (next to the date helpers, all on UTC day numbers): `workDaySet()` (cached by the identity of `project.workDays` — replace the array, never edit it in place), `isWorkNum/nextWorkNum/prevWorkNum/addWorkNum/countWorkNum` and their ISO wrappers `isWorkDay/nextWorkDay/prevWorkDay`, `shiftWork(iso, k)` (first to the working day on or after `iso`, then `k` working days, negative = a lead) and `calendarLabel()`. A whole week of working days is exactly 7 calendar days, so long moves jump by weeks.

**Semantics.**
- **`durationDays(start, end)` = working days from start to finish inclusive, never less than 1** (a legacy task sitting entirely on days off counts 1). `finishFor(start, dur)` is its inverse. Duration is still *derived* from the dates (nothing is stored), so it is what the Duration column, the dialog, Remaining Duration, the critical path and the Excel export all show — in working days.
- **Dependencies.** Lag and lead are **working days** (there is no "elapsed days" unit). `constraintStart()`: FS = the working day after the predecessor's finish plus the lag (`shiftWork(addDays(finish, 1), lag)`), SS = `shiftWork(linkStart, lag)`, FF/SF = the finish target `shiftWork(…, lag)` minus `dur − 1` working days; every result is a working day. `linkEnd()`'s projection for a started, unfinished predecessor is `finishFor(actualStart, planned duration)`. SNET/MSO/FNET/MFO bounds snap to a working day (an MSO on a Saturday therefore lands on Monday and shows the constraint-violated icon — MS Project flags it the same way). Cascade, `applyConstraints`, `rescheduleAsAuto` keep the task's working-day duration when they move it (`finishFor`).
- **Auto Scheduled tasks start and finish on working days; Manual tasks keep exactly the dates they were given** (their *duration* still counts working days). `snapToWorkDays(t)` (start → next working day, finish → previous one but never before the start; a milestone's finish = its start) is applied when you edit Start/Finish/Duration in the list (with a toast "Moved to a working day — this plan works Mon–Fri"), in the dialog (live, on the inputs, and again on Save), when you drag or resize a bar on the Gantt (the preview already shows the snapped dates; a move keeps the task's working-day duration), in `rescheduleAsAuto()` (a task with no links to place it by), and for a new task (`addTask()` starts an Auto task on `nextWorkDay(today)`, a Manual one on today).
- **Gantt**: days off are shaded (`.gantt-nonwork`, one band per run of non-working days, drawn under the bars, `pointer-events: none`) at Week and Month zoom; not at Year zoom (1.5px a day is just noise). Nothing is shaded when every day works. The Excel Gantt sheet (one column per week) is unchanged.

**Existing plans.** The default applies to them too, but **no date is moved when a plan is opened or its calendar is changed**: only the *counting* changes, so an old task Sat 19.09 → Fri 23.10 that used to say 35 days now says 25. Later scheduling follows the calendar (a successor that used to start on a Saturday moves to Monday the next time it is pushed). *Every day* restores calendar-day counting exactly. Changing the calendar never re-plans anything — a deliberate choice: re-planning would move every Auto task.

**Holidays** (`project.holidays`, an explicit user request): days off on top of the weekdays — `[{ date: 'YYYY-MM-DD', to?: 'YYYY-MM-DD', name?: string, yearly?: true }]`: one day, a range (`to` = its last day), or a single day that comes back every year (`yearly`, expanded for 2000–2100; 29 February only in leap years). Set in the same dialog as the weekdays (plan menu → Working calendar…: date / to / name / "Every year" + Add, a list with ✕; `openCalendarModal` / `addHoliday` / `removeHoliday` / `saveCalendar` edit a draft `calHolidays`, "Every year" is disabled once a last day is given). `cleanHolidays()` (called from `normalizeData()`) keeps real ISO dates only, a range only when `to` is after `date` (max ~10 years), `yearly` only for a single day, names ≤ 60, no duplicates, sorted, at most 400, and the key is **absent when empty**; the array is only ever replaced (the calendar cache is keyed by its identity, like `workDays`). In the calendar layer `workDaySet()` also rebuilds `holSet` (every holiday day number, ≤ 40000) and `holSorted` (those on a *working* weekday, for counting); `isWorkNum(n)` = the weekday works **and** `!holSet.has(n)`; `countWorkNum` subtracts the holidays inside the range by binary search; `addWorkNum` only takes the whole-week shortcut when there are no holidays (otherwise it walks day by day). Everything else — durations, lags, `finishFor`, `shiftWork`, snapping of Auto tasks, variances, the critical path, the Gantt shading (a holiday next to a weekend joins its band; shading is on whenever a weekday or a holiday is off) — follows automatically. `holidayName(n)` gives the name, `calendarSummary()` the `Mon–Fri · 3 holidays` text (menu hint, toast). Like the weekdays, holidays never move existing dates; they travel with the plan (merge: the project field `holidays`, described as `N holidays` in the conflict list). Covered by `verify_holidays.py` (45 checks) and the stress test's calendar operation.

**Public-holiday presets** (in the same dialog: a country / region select, from–to years, **Add public holidays**): rules, not lists, so any year works — `HD.fix(month, day, name)`, `HD.easter(offset, name)` (`easterSunday(y)`, the Gregorian computus), `HD.nth(month, weekday, n | -1 = last, name)`, `HD.before(month, day, weekday, name)` (the weekday strictly before a date: Repentance Day = the Wednesday before 23 Nov; Victoria Day = the Monday before 25 May), `HD.fn(name, f)`; `from` / `to` limit a rule to the years it applies to (Berlin's Women's Day from 2019, Mecklenburg-Vorpommern's from 2023, Reformation Day in Bremen / Hamburg / Lower Saxony / Schleswig-Holstein from 2018, Juneteenth from 2021, St Brigid's Day in Ireland from 2023 — the first Monday of February, or 1 Feb when that is a Friday); `sub: 'us'` moves a weekend day to the Friday before / Monday after (observed), `sub: 'uk'` to the next free weekday (Christmas Saturday → Monday, Boxing Day Sunday → Tuesday). `holidayPreset(regionId, y0, y1)` returns `[{ date, name }]` sorted, one per date. Regions (`HOLIDAY_REGIONS`): Germany nationwide and each of the 16 states (`DE_STATES` says what a state adds to `DE_BASE`), Austria, Switzerland (widely observed days; cantons differ), UK England & Wales / Scotland / Northern Ireland, Ireland, US federal, Canada federal, France, Netherlands, Belgium, Spain (national), Italy. `addHolidayPreset()` adds the days that fall on a **working weekday of the dialog's current chips** and are not already in the list (single days with their English names), remembers the region in `localStorage["milestone-holregion"]`, and tells how many it added and how many fell on days off anyway; up to ten years at a time, 2000–2100. A starting point, not legal advice (the dialog says so). Covered by `verify_holiday_presets.py` (43 checks: known dates for every rule type and many regions, the substitute-day rules, year limits, the dialog).

**Not modelled** (each would be a natural next step): working hours, per-task or per-resource calendars, elapsed-day lags (`ed`), holidays of other countries, and re-planning the schedule when the calendar changes.

**Tests.** `verify_calendar.py` covers the Mon–Fri behaviour (durations, all four link types with lag/lead, actual-date projection, snapping in the list / dialog / drag, new tasks, the shading, the dialog, persistence, garbage input). The older suites (`verify_actuals`, `verify_columns`, `verify_filters`, `verify_excel`, `drive_taskmode_*`, `verify_gantt_scales`) were written in calendar days, so each sets `project.workDays = [0,1,2,3,4,5,6]` right after its first reload; their assertions are unchanged.

### Robustness rules found by the stress test (`verify_stress.py`)

A seeded random test (`verify_stress.py`: 400 random operations per seed — add, delete, indent, outdent, drag-move, Start/Finish/Duration/predecessor/actual-date edits through the real commit path, Gantt bar drags, mode switches, clone, baselines, working-calendar and holiday changes, milestone and constraint changes, toast undo, history undo/redo and an undo→redo round trip, view/zoom/column changes — then invariants after **every** operation: unique ids, valid dates, no parent cycles or dangling/self/group links, milestones one date, progress 0–100, baselines only on leaves, an Auto task that has not started sits exactly where its links put it (`constraintStart`) and on working days, display ids unique, both views render; every 20 steps `normalizeData()` is idempotent, merging the plan with itself changes nothing and save → load → save is byte-stable; every 10 the critical path is checked (whole-number floats, something critical, the last finisher critical), every 60 the Excel export builds) found real defects, now fixed — keep these rules:
- **A selected task that disappears** (deleted on another device, replaced by an import or a merge) must not break `render()`: `render()` and `updateSelectionUI()` clear `selectedTaskId` when the task is gone.
- **A group's own Start/Finish follow its tasks** (`normalizeData()`, auto groups only, snapped to working days) — they are unused while it is a group but are what it falls back to when it stops being one. A task with tasks in it is never a milestone (the flag is cleared).
- **A group that loses its last task** (outdent, drag-move, delete) is an ordinary task again, so its own links/constraint apply: `releaseGroup(id)` → `applyConstraints()`. `deleteTaskFlow()` also re-checks the survivors that lost a predecessor (one released from a dependency cycle must be placed); its Undo puts their dates back.
- **Breaking a dependency cycle releases its tasks**: a task in a cycle is never placed by the scheduler, so when a link is removed (inline Predecessors edit, dialog save), a task is deleted or a task drops out by being turned into a group (drag-move, indent), `releaseFromCycles(before)` runs `applyConstraints()` on every task that is no longer in the cycle set (`before` = `taskCycleSet()` taken before the change). `deleteTaskFlow()` includes those tasks in its Undo snapshot. **Undo of a delete can come after other edits** (the toast lasts a few seconds): it takes a re-planned survivor's dates back only if that task still has the dates the re-plan gave it (`ns/ne` — otherwise a later edit would be overwritten), and afterwards runs `applyConstraints()` on every restored task and every task whose link came back if it now starts before its links allow — unless it already did before the delete (`earlyBefore`; `startsBeforeLinks()`), so a task the user deliberately placed early comes back exactly as it was. Cloning a cycle member places the *copy* (it is not in the cycle) — nothing else in a clone is moved.
- **Group dates reach a fixpoint** (`normalizeData()`): an Auto group whose tasks are all unscheduled (TBD) falls back to its *own* stored dates, which the same step snaps to a working day — a group above it may already have read the old value. The step therefore repeats (at most 8 passes, cache reset each time) until nothing moves. Found by fuzzing `normalizeData` on random plans (about 1 in 1,300 was not idempotent, and the result depended on the order of the tasks in the array — i.e. two devices could have written different bytes for the same plan and kept re-syncing). `verify_normalize.py` keeps it fixed: 9,000 random plans, idempotent, order-independent, a merge with itself changes nothing.
- **Undoing a delete restores the chain downstream** (`deleteTasksNow()`'s toast Undo): deleting a predecessor pulls not only the tasks that lost a link but everything behind them earlier (bidirectional scheduling); the undo's record (`replanned`) holds only the tasks that lost a link, so the tasks further down stayed where the delete had pulled them. It now ends by `cascadeSchedule()` from every task that came back, lost a link or was re-placed. Found by the stress test under load (about 1 seed in 200, order-dependent); `verify_pull.py` has the deterministic case (E → X ← D, Y and Z behind X: delete D, Undo, everything back on its dates).
- **Numbers are bounded** (found by the monkey test, `verify_monkey.py`: a duration of `99999999999` typed into the task dialog froze the page — with holidays in the plan `addWorkNum()` walks day by day, so an absurd move meant billions of steps). A **duration** is at most `MAX_DURATION_DAYS` = 9,999 working days and a **lag / lead** at most `MAX_LAG_DAYS` = ±9,999 wherever a person can enter one: the dialog (clamped, `max="9999"`), the inline Duration cell and Predecessors cell (refused with a message, nothing changes), bulk edit ("Move dates by" ≤ 5,000, lag ≤ 9,999), `parseTableDuration` / `parsePredText` (an absurd duration is not a duration, an absurd lag is an unreadable link) and `normalizeData()` (every predecessor's lag is rounded and clamped — so a plan file, a merge or an import can't bring one in). `addWorkNum()` itself caps any move at 40,000 working days (~150 years) as the last line of defence. `verify_robust.py` tries every entry point with 99999999999 / 1e12 / 1e300 and times it. `verify_monkey.py` has a 60-second watchdog per action that reports the last actions if the page ever stops answering.
- **Crossed dates are fixed before the cascade, not after**: `clampTaskDates(t)` (Finish not before Start, a milestone one date, a finished task's Actual Finish not before its Actual Start and equal to its Finish) runs in the inline commit paths and the dialog save *before* `snapToWorkDays()` / `cascadeSchedule()`; `normalizeData()` also clamps Actual Finish ≥ Actual Start. Otherwise a successor is scheduled off dates `normalizeData()` corrects only on save.
- **Clearing an actual date** makes the task un-started again: it is snapped back to working days (`snapToWorkDays()`), inline and in the dialog.
- **Clearing an actual date leaves the schedule where it was** (documented above), so the stress test's "Auto task obeys its links" invariant exempts a task that has ever had an actual date during the run.
- Changing the **working calendar never moves dates** (by design), so the stress test switches the "on working days / obeys its links" invariants off after a calendar change.
Covered too by `verify_e2e.py`: a scripted user journey with real clicks (dialog, indent, dependencies, inline edits, baseline, actual dates, calendar, filters, Gantt drag/zoom/critical path, separate column sets, clone/delete/undo, Excel and JSON export, import/replace, backups, plans, theme, help, reload persistence) with zero console errors.

### Task IDs are collapse-stable, and drive predecessor/successor selection

`taskDisplayId(id)` is a task's 1-based position in the *full* outline order (every task, ignoring `collapsed`) — deliberately not `visibleTaskList()`'s own collapse-aware order, which is what row rendering uses. This is what makes an ID usable as a stable reference at all: collapsing a parent elsewhere must never renumber a still-visible task's own ID, or a predecessor link recorded by id (the data itself is always stored by internal `task.id`, never by this display number) would read as pointing to a different row than the one a user actually picked. `resetIdCache()`/`_idIndexCache` follow the identical per-render-pass caching shape `resetEffectiveCache()`/`_effCache` already established.

Every place a task is chosen or shown as a predecessor/successor leads with this ID, not its name: the grid's own Predecessors column reads as a compact `3FS+2`-style reference (id + dependency type + signed lag) rather than a truncated task name — both shorter and immune to a later rename, matching how real MS Project's own Predecessors column reads. The task modal shows the task's own ID and WBS code as a badge next to its title (`#taskModalIdBadge`, e.g. `#4 · WBS 2.1`). There used to be a read-only **Successors** list under Predecessors in the dialog; it was **removed at the user's request** (`renderSuccessorsList()` and its CSS are gone). `successorsMap()` stays — `cascadeSchedule()` needs the reverse index.

**The predecessor picker is a plain numeric field, not a dropdown — an explicit user request, and also just how real MS Project's own Predecessors column works: type the task's number directly.** `onPredecessorIdChange(i, value)` resolves the typed number via `taskIdByDisplayId()` (the reverse of `taskDisplayId()`) on blur/Enter, not on every keystroke — a self-reference, a nonexistent ID, a summary task, or a duplicate already in the list all get rejected with a toast and the field clears back to empty rather than silently accepting something wrong; a freshly-added row starts genuinely empty (`{id: null, ...}`) rather than defaulting to an arbitrary task the way a `<select>`'s own first option would. `saveTaskFromModal()`'s existing `editingPredecessors.filter(p => p.id)` is what quietly drops a row that's still empty or still invalid at Save time, with no separate validation step needed. The field's native up/down spinner is hidden via `.pred-id-input` CSS (`-webkit-appearance:none` on the spin buttons, `-moz-appearance:textfield` on the input) — it was resolving/replacing a typed ID rather than doing anything useful, since a Task ID isn't a value you'd ever want to increment.

### Inline grid editing (Task view only)

`editingCell` (`{id, field}` or `null`) tracks which single cell, if any, is mid-edit — pure transient UI state, not persisted, reset by `setView()` and `openTaskModal()` so a stray edit never survives a view switch or the modal taking over. `renderGrid()` swaps that one cell's static `<div>` for an `<input>` (via each cell's local `editing('field')` check) rather than reworking the whole row into a form; every other cell keeps rendering normally. Clicking a static cell calls `startInlineEdit(id, field)`, which re-renders and then focuses/selects the new input on the next frame (the input doesn't exist yet at click time). Enter blurs the input (triggering commit); Escape calls `cancelInlineEdit()` directly, clearing `editingCell` before the resulting re-render can remove the focused input out from under a pending blur — `commitInlineEdit()` guards on `editingCell` still matching `{id, field}` so that stale blur is a no-op instead of double-committing or committing after cancel.

**Selecting text in an editor must not end the edit** (user report: "if I edit a field, select the word and then leave the box, it stops the edit"). Two mechanisms did it, both fixed: (1) a **double-click** on a word in the open editor bubbled to the row's `ondblclick` and opened the task dialog (which resets `editingCell`) — the row now calls `rowDblClick(event, id)`, which ignores a double-click that lands in `.inline-edit` / `.inline-wrap`; (2) a **drag-select that is released outside the input** produces a `click` on the common ancestor (the row or the list), so `selectTask()` re-rendered the row and destroyed the editor — a capture-phase `mousedown` listener sets `mouseDownInEditor` when the press started inside the open editor, and `selectTask()` swallows exactly that one click. One consequence: a double-click on an *editable* cell (its first click opens the editor, the second lands in it) now selects a word instead of opening the task dialog — as in Excel; the dialog opens from the Edit button, the ID / Mode / WBS cells, cells that have no editor and the row's gaps (`verify_e2e.py` / `verify_reorder.py` double-click the ID cell). A click on *another* row, on the empty area, Enter and Escape behave as before (commit / commit / cancel). Covered by `verify_inline_select.py` (27 checks: double-click and drags to every side for the name, resource, manual-date text, custom text and duration editors, in both views, plus the regressions).

Only leaf tasks get start/finish/duration/predecessors inline editing — except a *manually scheduled* summary, which owns its own dates and so gets start/finish/duration too (an Auto summary's dates are computed rollups — see `effectiveDates()` above — so there's nowhere to write); milestones additionally skip finish/duration (forced equal to start by definition). Auto tasks get the native date input; Manual tasks get the free-text editor described under Task Mode. **% complete is editable inline for a task without sub-tasks** (a user request; the `%` cell, `startInlineEdit(id, 'progress')` — a group's % is a rollup, so it stays read-only): a text box that accepts `50`, `50%` and `12,5` (rounded to a whole number), empty leaves the value, anything outside 0–100 or not a number is refused with a toast and nothing changes. It only sets `progress` — like the dialog and bulk edit it does not touch actual dates (the coupling runs the other way: recording an Actual Finish sets 100%). Covered by `verify_progress_inline.py` and the stress test's `progress` operation. `commitInlineEdit()` stamps `updatedAt` (inline edits previously didn't, which would have let a stale copy win a last-write-wins merge). All of this mirrors the task modal's own rules, just enforced at the point where the click would start an edit rather than after the fact.

Typing into the inline Predecessors cell is read **the way MS Project writes links** (an explicit user request after asking whether the syntax matched) with the same reader as paste and import, `parsePredText(str, strict)`: `3`, `3FS`, `3SS+2d`, `4FF-1w`, `2FS+4h`, `+1 week`, several separated by `,` or `;`, case-insensitive, the German `EA/AA/EE/AE`; lags are **working days** (`w` = 5 days, `h` = ⅛ day, rounded). In this strict mode a lag unit must be d / w / h (or their long and German spellings): **elapsed lags (`+2ed`) and percentages (`+50%`) are refused** with a message (`predBadMessage()`) instead of being read as working days, as an unknown unit is; paste and import stay lenient. The label written back is unchanged (`3FS+2`; MS Project would show a zero-lag FS as `3` — deliberately left), a decimal comma splits the list (use a point or `;`), and the cell's tooltip explains the syntax (no placeholder). Covered by `verify_pred_syntax.py` (43 checks). Otherwise as before: it reuses the same compact `3FS+2` syntax the grid displays (`parsePredecessorString()`), but unlike the modal's per-row picker this one field represents the task's *entire* predecessor list at once — so a single bad token (typo, self-reference, summary task, unknown ID) rejects the **whole** edit and leaves the existing list untouched (returns `null`, `commitInlineEdit()` skips the assignment) rather than silently keeping only the valid tokens and dropping the rest. Losing an already-correct predecessor to an unrelated typo elsewhere in the same string would be a much worse failure mode than just rejecting the edit outright.

Empty grid cells (no predecessors yet, blank duration) used to collapse to zero height under `align-items: center`'s default content-sizing, making an empty Predecessors cell unclickable — `.grid-cell-dim` now sets `min-height: 1em; align-self: stretch; display: flex; align-items: center` so a cell with no text still occupies its full row height.

**Date editors are compact and fit their (104px) column.** Start, Finish, Actual Start, Actual Finish and custom Date cells all edit with either the native `<input type="date">` (Auto tasks) or the typed box + calendar button (`.inline-wrap`, Manual tasks). They used to be ~132px wide with the browser's padding around the fields, a 24px picker indent and a second (browser) focus ring on top of the accent border. Now: `input.inline-edit { outline: none }` (the 1px accent border *is* the focus indicator, for every inline editor); the native control's own padding is removed (`::-webkit-datetime-edit(-fields-wrapper) { padding: 0 }`) and its picker icon shrunk to 13px; font 12px, padding 2px. Result: native editor `max(100% − 4px, 95px)`, typed editor `max(100% − 4px, 92px)`, both ~21px tall, text starting where the cell's text does (2px margin + 1px border + 5px padding = 8px). **Every date column is 104px wide** (Start, Finish, Actual Start/Finish, custom Date) = 2px + a ~100px editor + 2px: the open editor sits *inside* its column with the same space to the line on the left and on the right and never crosses into the neighbour (an earlier 92px column made it spill over the line). If you change the font or these widths, re-check that "2026" and the picker icon are fully visible in the native editor (Chromium can't report this through `scrollWidth`; look at a screenshot; the OS/browser region format, e.g. `dd.mm.yyyy` with its wider separators, can't be emulated in headless tests — leave a few px of slack). Covered by `verify_date_editors.py`.

### Column lines and cell spacing (the task list, in both views)

**Spacing rule — one for every column.** The task list has **no gap between tracks** (`column-gap: 0`) and every cell keeps the same **8px inset from the column line on both sides**: `padding-inline: 8px` on all cells except the ID cell (first) and the row-actions cell (last), and a `4px` margin on the inline editors (which are grid items themselves; date editors additionally grow to 132px while open, see above). Task Mode and Flag cells no longer centre or indent themselves; the header labels use the same inset, so header and content line up. **The Name column is the deliberate exception**: its text keeps the original indent — `calc(3px + --depth × 16px)` from the line (the outline depth is passed as `--depth`; the Gantt side list uses `depth × 16px` without the 3px) — plus 8px on its right end. (An earlier attempt gave it the 8px inset too; the user preferred the original indent, so it was reverted.)

**Column widths include that inset**: width = widest header (label + 3px gap + 18px funnel) or content + 16px, measured from real text (see the comment above `TASK_COLS`): Task Mode 76, WBS 104 (eight levels, `2.2.2.2.2.2.2.2` = 83px of text in the widest digit, plus the inset and a little slack; a ninth level would be cut with an ellipsis), all date columns (Start, Finish, Actual Start/Finish, custom Date) 104 (sized for the open date editor, not for the closed text), Duration 104, % 56, Predecessors 136, Remaining Duration 110, Status 108, custom Text 130 / Number 100 / Flag 80. Keep new columns on this rule rather than eyeballing them.

**The row-actions column has a header** — an `Actions` label (`.actions-head`, plain text, no filter funnel) with the usual column line to its left — and is `88px` wide (2px + three 24px buttons + gaps + slack). Its buttons start at the same 8px inset as the header label (`.grid-actions { padding-left: 2px }`: the first icon's glyph sits 6px inside its 24px button), and stay hover-only.

**Horizontal scrolling and frozen columns.** When the visible columns are wider than the list (the window in the Tasks view, the resizable list pane in the Gantt view) the list **scrolls sideways** (before this it silently clipped everything past the window edge — the right-hand columns and the row actions were unreachable). `#gridRows` is `overflow: auto` in the Tasks view (still `hidden` in the Gantt view, where its scrollTop is driven programmatically). The row can't get narrower than `--grid-min-w` (set in `renderGrid()`: ID + every visible column at its fixed width, Task Name at its 160px minimum, the actions column, plus the row's 2×10px padding) — with the default columns that is **986px**, with Actual Start/Finish, Status and Resource added **1442px** — and `.grid-row` / `.grid-header` carry `min-width: var(--grid-min-w)`. `.grid-pane` has `min-width: 0` (a flex item would otherwise grow to its content).
- **The header follows**: `#gridHeader` sits in `#gridHeaderClip` (`overflow: hidden`, never scrolled by the user); `syncHeaderScroll()` (on the rows' `scroll` event, after every render and from the pane's `ResizeObserver`) copies `scrollLeft`, gives the clip the rows' vertical-scrollbar width as right padding (so both have the same width, and the fr column is the same size in both) and toggles `.h-scrolled` on `#gridPane`. A sideways wheel/trackpad gesture over the header scrolls the rows.
- **Frozen columns** (like Excel's freeze panes): the ID column and **everything up to and including Task Name** stay put (`updateFrozenColumns()` runs after every render — cells are brand new each time — marks them `.frz` (the last one also `.frz-last`) and sets each `left` = the row's padding + the tracks before it). They are `position: sticky` with `z-index: 3`, `align-self: stretch` (a cell is otherwise only as tall as its content and the scrolled columns would show above and below it; inputs that are grid items are exempt), and they paint `--row-bg`: the row's background is now the custom property `--row-bg` (`--panel`, or `--panel-2` on hover, the accent tint when selected / a drop target) so the frozen cells always match it. The first frozen cell also paints a `-10px` box-shadow in `--row-bg` over the row's left padding (where scrolled content would otherwise peek out). Their right-edge column line is an inset box-shadow (the opaque cell covers the row's own line), with a soft shadow on the last one while `.h-scrolled`. If Task Mode / WBS are hidden, only ID + Task Name freeze; the name editor sits inside the frozen Name cell.
- **Drop indicators moved** from `box-shadow` on the row (which the opaque frozen cells would have covered) to a 2px accent bar on `.grid-row::after` (`z-index: 6`, top for *before*, bottom for *after* / *into*).
- **The lines in the empty area** under the last task use `background-attachment: local` so they scroll with the content, and are switched off while `.h-scrolled` (they would cross the frozen columns; the rows keep their own lines).
- Covered by `verify_hscroll.py`.

**Column lines.** A fine vertical line in `var(--border)` — the colour of the divider between list and chart in the Gantt view — separates the columns, in the header and in every row, and runs on down the empty area under the last task. **They are not cell borders**: the tracks mix `px` and `fr`, and the date editors overflow their cell, so borders would fight all of that. Instead `updateColumnLines()` (called from `render()`, and by a `ResizeObserver` on `#gridPane`, falling back to `window.resize`) reads the *resolved* `grid-template-columns` of `#gridHeader` and of the first row, puts a line on each track boundary (the last pixel of the left cell; the boundary before the row-actions column included) and publishes them as CSS variables on `#main`: `--col-lines-h`/`--col-pos-h` (header) and `--col-lines-r`/`--col-pos-r` (rows; measured separately because a scrollbar can narrow the rows only). `.grid-header::before` / `.grid-row::before` (absolute, `pointer-events: none`) paint them as 1px gradient layers, `.grid-rows` paints the row variable for the empty area below (rows are transparent, so they coincide; a hovered/selected row's own background can't hide its lines because they live on the pseudo-element). All of this applies to the list in the Gantt view too (see "The Gantt view's left side is the same full task list"); with no rows the header keeps its lines and the body has none. Covered by `verify_column_lines.py`.

### Where Add Task puts the new task

`addTask()` inserts the new task **directly below the selected one** (an explicit user request): right after a leaf task as its sibling, or as the *first sub-task* of a summary task (expanding it if it was collapsed so the new row isn't hidden); with nothing selected it's appended to the end of the top level. The new task becomes the selection, which is what makes repeated Add Task stack downward — without that, every add would land directly under the *same* selected row and the run would come out reversed. The level's siblings are then renumbered `0..n` with the new task in its slot; only siblings whose `order` actually moved get a fresh `updatedAt`, since `order` is a merged field and an un-stamped renumber would never reach another device (the same rule `reorderItem()` follows in Pulse).

### Empty lines (spacer rows)

An explicit user request ("add a button to add an empty line"; the answer to which meaning was a *spacer row*, not a placeholder task). **`addSpacer()`** (`#addSpacerBtn`, the lines icon right of Add Task) inserts a task with `spacer: true` **directly below the selected task, at its level** — below a group's *whole block* (not as its first sub-task, unlike Add Task), below a sub-task inside its group, at the end of the top level when nothing is selected — selects it (so pressing again stacks lines) and opens no dialog.

- **What it is**: a record like any task (so ordering, indent/outdent, drag, clone, copy/paste, delete, undo, the tombstones and the merge need no special code) whose fields `normalizeData()` keeps empty: `name ''` (the only place a name may be empty — `Untitled Task` is not applied), no links, `%`, resource, colour, custom values, baselines, actual dates, constraint; `taskMode 'manual'` (so the scheduler and the critical path skip it); `startDate/endDate` are stored placeholders (today) that nothing reads. `isSpacer(t)`; **`isUnscheduled(t)` is true for it**, which already gave it no bar, no rollup contribution, no place in date ranges and no role as a predecessor. Extra normalisation: a task filed under a line moves up to the line's own parent (a damaged file or merge; the UI never does this), a link *to* a line is dropped, and `spacer` is deleted when not `true` (the key is absent for ordinary tasks).
- **Numbers**: it **has an ID** (its place in the outline, like MS Project's blank rows — so inserting one shifts the IDs below it, and a typed predecessor number means what the list shows) but **no WBS code and does not count in the WBS numbering** (`wbsCode()` skips it).
- **The row** (`.grid-row.spacer-row`, faintly tinted; `.gantt-row-bg.spacer` in the chart): the ID and blank cells, no editors (`startInlineEdit`, `commitInlineEdit`, `setTaskMode`, `toggleCustomFlag` and `openTaskModal` return for it), no Edit button (Clone and Delete stay), double-click does nothing, no bar or bracket. It has a chevron placeholder so depth indents line up.
- **Where it is deliberately left out**: predecessor entry (inline, dialog, bulk — "Can't depend on an empty line"), Indent *under* a line ("Can't indent under an empty line"; a line itself can be indented/outdented), Find (`#n` and name/WBS/resource searches), bulk edit (the button is disabled when only lines are selected; lines in a mixed selection are ignored and not counted), column filters (`filterShows()` hides a line while a filter is on unless it was just added — a rule such as "does not contain" would otherwise let a blank row through; also the filter-list values and the "N of M tasks" chip), the Excel dialog counts, `computeDateRange()`.
- **Copy / print / Excel**: copy gives a table row with only its ID (`clipCell`), and the private format carries the flag, so a paste brings the line back; Print draws the ID and nothing else; the Excel Tasks and Gantt sheets write the ID and empty bordered cells (the outline is exported in full, so the separators are kept). History describes it as "an empty line" (`taskLabel()`, `describeChange`); delete / clone messages say "empty line" and Clone makes another line (no " (copy)").
- Covered by `verify_spacer.py` (54 checks: placement in every selection state, IDs and WBS, the row, damaged data, predecessors, indent, moving, clone / delete / undo / redo, copy / paste, bulk edit, find, filters, Excel, print, reload, merge, help) and, in `verify_stress.py`, an `spacer` operation plus the invariant "an empty line stays empty, nothing depends on it, it is never critical". The plan checker of `verify_robust.py` / `verify_monkey.py` accepts an empty name only on a line.

### Clone task (`cloneTask(id)`)

A **Clone** button on every task row (Tasks view; it appears on hover between Edit and Delete — the row-actions column is 88px for the three buttons) and one in the toolbar's selection buttons (`#cloneTaskBtn`, **labelled "Duplicate"**, acts on the selected tasks) and in the right-click menu. It copies the task **and everything below it, at every depth**:

- **Exact copy**: each task is a `JSON` deep copy (dates, %, actual dates, mode, constraint, colour, resource, milestone flag, custom fields, free-text dates …) with a **fresh id**; sub-tasks get their cloned parent's id. Only the top task's name gets ` (copy)`; the sub-tasks keep theirs. `updatedAt` = now, so a sync sees new tasks.
- **Placement**: directly under the original at the same level (its sibling, `order + 1`); that level is renumbered, and only siblings whose order really moved get a fresh `updatedAt`. The clone is selected, added to `filterPinned` (an active filter can't hide it), and keeps `collapsed` as the original had it. The dialog is *not* opened.
- **Dependencies**: a link **between cloned tasks** is re-pointed at the clones (type and lag kept, at any depth); a link to a task **outside** the clone is kept, so the copy is scheduled exactly like the original; nothing outside the clone starts depending on it. (Summary tasks can't have predecessors — `normalizeData()` strips them — so only leaf tasks carry links.) The clone sits on the same dates, so nothing moves — except the copy of a **dependency-cycle member** (the scheduler never placed the original): the copy is not in the cycle, so it is placed by its links (`applyConstraints()` on those copies only — a task the user placed ahead of its links is still copied exactly; found by `verify_stress.py`, seed 35).
- **Undo** (toast): removes every clone, tombstones their ids (`deletedTaskIds`, so a sync can't resurrect them), restores the moved siblings' order and the previous selection.

### Task fields and columns

Besides name, dates, duration, %, predecessors and a colour, a task has **stored** fields `resource` (free text, ≤200 chars), `actualStart` and `actualFinish` (real dates or null; sanitised by `normalizeData()` via `parseUserDate`), and **computed** ones that are never stored:

- **WBS** — `wbsCode(id)`: the outline position as `1`, `1.1`, `1.2.3` (like MS Project's default WBS), cached per render in `_wbsCache` (cleared by `resetIdCache()`; the Excel export calls it too). Like the ID it ignores collapsing and filtering, and it renumbers itself on reorder/indent. Read-only — there is no custom-WBS override.
- **Actual Start / Actual Finish** — `actualDates(id)`: a task's own; a group **rolls up** — the earliest actual start of anything below it, and an actual finish only once *everything* below has one (then the latest). A group's cells and dialog fields are read-only (the dialog says why) and saving a group never writes its rolled-up dates into itself. An Actual Finish before the Actual Start is refused (toast) in both the inline editor and the dialog; the dialog checks *before* changing anything. **A milestone happens on one date, planned and actual**: like `endDate = startDate`, `normalizeData()` forces `actualFinish = actualStart`; the dialog hides **Actual Finish** together with Finish and Duration (`#taskActualFinishField`, toggled in `onMilestoneToggle()`), the list's Actual Finish cell isn't editable for a milestone, and editing its Actual Start moves both — so a milestone with an actual date is `Complete` (it has happened) with no extra rule in `statusOf()`. (Actual Finish used to stay visible on milestones while Finish was hidden, which read as "Finish is missing".) **They do not couple to % complete** (MS Project sets 100% on an actual finish; not done here). **A task's own planned dates are never rewritten by its own actuals — but its successors are scheduled off them:** see the next section.
- **Remaining Duration** — `remainingDays(id)`: `duration × (1 − % complete)` in days, one decimal (`2.5 days`); blank for milestones and free-text durations.
- **Status** — `taskStatus(id)`, judged against *today*: `Complete` (100 %, or an actual finish), `Late` (not complete and past its finish, or should have started and hasn't), `Future Task` (not started, start ahead), `On Schedule` (everything else); blank when there is nothing to judge. "Started" = some progress *or* an actual start. Shown as a coloured pill (`.status-pill`).

**The task dialog shows every field.** Stored ones are inputs (Resource sits beside Task Mode; Actual Start/Finish under Duration/%). The three *computed* ones — **WBS, Remaining Duration, Status** — appear in a dashed read-only row (`.calc-row`, `.ro-value`) under the actual dates, so nothing that is a column in the list is missing from the dialog. `updateModalComputed()` refreshes that row from what is **currently typed** (it uses the pure helpers `remainingOf()` and `statusOf()` that the list columns also use, via `remainingDays()`/`taskStatus()`), so it follows edits live; it is wired as an `input`/`change` listener on `#taskModalBg`, which runs after each field's own `onchange` has synced the dates and duration. A group shows its rolled-up values, and a task whose dates are still free text ("TBD") shows "—" until it is given real dates (`modalOrigDates` tells untouched from edited). Nothing here is stored. The dialog is `.modal.wide` (620px) with a four-column grid; see "Dialog usability" below for the layout, and for the warning before edits are thrown away.

**Custom fields** (an explicit user request): **Text1–5, Number1–5, Date1–5, Flag1–5** — 20 fields per task, hidden by default, enabled in the column picker, shown in their own tab of the task dialog, renamable, with the names **kept per plan**.

- **Storage.** A task's values are `task.custom` (`{ text1: 'x', number2: 4.5, date3: '2026-09-01', flag4: true }` — a flag is stored only when set, and nothing empty is stored; the object disappears when it would be empty). The *names* are `project.fieldNames` (only the ones that differ from the default `Text1`…), which is why they belong to the plan: they are part of `syncPayload()`, so they are exported, backed up, written to the plan's file and merged (last write wins on `project.updatedAt`, which renaming stamps), and two plans can call the same field different things. `cleanCustomValues()` and the block at the end of `normalizeData()` sanitise both on every load/merge/import: unknown keys dropped, text trimmed and capped at 255, numbers must be finite (`12,5` is accepted), dates must be real, names trimmed, capped at 40, and a name equal to the default is dropped.
- **Registry.** `CUSTOM_KINDS` / `CUSTOM_FIELDS` define the 20; each is also an entry in `TASK_COLS` (`custom: true`, `dflt: false`) and `FILTER_COLS` (text → text rules, number → number rules, date → date rules, **flag → a Yes / No list**, Yes first), whose `label` is a **getter** (`customFieldName(id)`), because it depends on the current plan. Because they are ordinary columns, the Columns menu, ordering, persistence and the "new columns arrive hidden" rule in `loadPrefs()` needed no special handling. **Field names are user text, so every place that puts a label into HTML escapes it** (header, menu, aria-labels, filter panel and chips, dialog tab).
- **The list.** `customCellHtml()`: Text/Number/Date click to an inline editor; a **Flag toggles on click** (`toggleCustomFlag`, a green tick). The inline **number editor is a text box** (`inputmode="decimal"`), not `type=number` — a native number box refuses to let you type the invalid part, so "12,5" or a typo could never be handled; it is parsed on commit (`isn't a number` toast, nothing changes). Any task can have custom values — groups and milestones included — and nothing is rolled up.
- **The dialog.** Two tabs, **General** and **Custom fields** (`.modal-tabs`, `setTaskModalTab()`); the dialog always opens on General and the Custom tab carries a badge with the number of values set (`updateCustomBadge()`, live). The tab is four sections (`renderCustomFieldsTab()`), inputs `cf_<id>`, read back by `readCustomInputs()`; Save writes both tabs. A validation error raised on the General tab (Actual Finish before Actual Start) switches back to General so it is visible.
- **Renaming.** A pencil beside each custom field — in the Columns menu and on the Custom tab — opens `#fieldNameModalBg` (`openFieldNameModal`/`saveFieldName`). A name must be unique among the custom fields *and* the standard columns (case-insensitive), 1–40 characters; an empty name, the default name, or **Use default name** removes the override. Renaming from the dialog re-renders the tab **with what is currently typed**, so unsaved input survives. The rename dialog sits after the task dialog in the page so it opens on top, and **Escape closes only the topmost one** (the general handler closes every open modal, which would have thrown away the task dialog's edits).
- **Excel.** "As shown" exports the enabled custom columns, headed with the plan's names (Date as a real date, Number as a number, Flag as Yes/No); "All columns" adds only the custom fields **in use** (renamed or holding a value), not twenty empty columns.
- **The Columns menu** now has 33 rows: it scrolls (`max-height` is set when it opens), keeps its scroll position across the re-render every tick/move triggers, and shows a rename pencil on custom rows.

**Default column sequence** (an explicit user request — the order the user arranged and asked to make the default): Mode, WBS, Name, Start, Finish, Actual Start, Actual Finish, Duration, %, **Predecessors, Remaining Duration, Status**, Resource, then the 20 custom fields. It is the insertion order of `TASK_COLS`; "Reset to default" restores it. Installs keep whatever order they have saved.

**Two-line column headers** (the list in both views): a header may run to two lines. `colHeadHtml()` turns a `\n` in a label into `<br>` — used for `Task/Mode`, `Actual/Start`, `Actual/Finish`, `Remaining/Duration` — and any other header (a long custom name) wraps naturally, clamped to two lines with an ellipsis (`-webkit-line-clamp`). This is what lets Task Mode be 76px wide (widths include the 8px cell inset — see "Column lines and cell spacing"). The header row is 42px there (task rows stay 32px); the Gantt view's side list keeps its one-line 32px header because it has to line up with the chart's timescale.

**The Predecessors column is only as wide as its header** (an explicit user request): a fixed `136px` — measured need is about 132px (header text 95px + funnel 18px + gap 3px on macOS, plus the 2×8px cell inset), plus a little slack for other fonts — where it used to be `1fr` and took a large share of the spare width; Task Name (`minmax(160px,1fr)`) is the one column that flexes — **every other column, Resource included (`140px`, it used to be `minmax(120px,1fr)` and split the spare width with Task Name), has a fixed width** (an explicit user request), so adding or removing a column never resizes the others. Long Resource text is cut with an ellipsis (tooltip and editor show it all). It must be a *fixed* width, not `max-content`: every row is its own grid, so a content-sized track would differ from row to row and the columns would no longer line up. A long reference list (`1FS+2, 2SS-1, 3FF+12`) is therefore cut with an ellipsis in the cell; the tooltip and the editor show all of it.

**Dialogs that fade in can't be focused on the next animation frame** — the element is still invisible then, so `focus()` silently does nothing. `openPlanModal` and the field-rename dialog used `requestAnimationFrame` and never put the cursor in their name field; they use a 40 ms timer now, like the task dialog does.

### Baselines, actual dates and variance (MS Project style)

An explicit user request: switch from "Start/Finish are the plan, actuals live beside it" to MS Project's model. **Start / Finish are the CURRENT schedule; a BASELINE is a frozen snapshot of it that the user takes on purpose; Start Variance / Finish Variance measure the distance between the two; and recording an actual date overwrites the schedule.** (Replaces the earlier model, where the planned dates were never touched and the Gantt drew a separate "actual span" bar.)

**Baselines** — `task.baselines = { slot: [start, finish] }`, **eleven slots like MS Project: 0 = "Baseline", 1–10 = "Baseline 1"–"Baseline 10"** (`BASELINE_SLOTS`, `baselineName(n)`). **Setting one is always a manual step — nothing is ever baselined automatically** (an explicit user correction: a first version baselined every plan on upgrade; that was removed). *Plan menu → Baseline…* (`#baselineModalBg`): pick the slot (each option shows when it was set and for how many tasks; the first free slot is preselected), pick the scope (*the entire plan*, or *the selected task and the tasks in it*), **Set baseline** (setting a slot again replaces it for the tasks in scope) or **Clear this baseline**; every set/clear has an Undo toast (`snapshotBaselines` / `restoreBaselines`). Only **leaf** tasks are stored (`applyBaselineChange()`; a manual task whose dates are still free text is skipped; a milestone stores one date); a **group has no baseline of its own — it shows the rollup** of its tasks' (`baselineDates(id, n)`: earliest start, latest finish of the tasks that have that slot; cached in `_baseCache`, cleared with the other per-render caches). A slot counts as *set* when some task has it (`setBaselineSlots()`); `project.baselines = { slot: { setAt: 'YYYY-MM-DD' } }` only adds the date, and `normalizeData()` prunes it for slots no task has and drops group / invalid / out-of-range data. **Which baseline is shown**: `project.compareBaseline` (default 0; the first baseline ever set becomes it; chosen in the same dialog, "Compare with…"): it drives the Baseline / Variance columns, the Gantt lines, the dialog's baseline line and the Excel columns. Both live on `project`, so they are saved, exported, backed up and synced per plan.

**Variances** — `scheduleVariance(id, n)` returns `{ start, finish, duration, baseDuration }` in **working days** (`workDiff()`, so it follows the plan's calendar; positive = later than the baseline): current Start − Baseline Start, Finish − Baseline Finish, Duration − Baseline Duration. Blank without a baseline (or for a task with free-text dates). `fmtVariance()` prints `+3 days` / `0 days` / `-2 days`; later is red (`.var-late`), earlier green (`.var-early`). Six columns, **hidden by default** and listed after Status in the column picker: *Baseline Start, Baseline Finish, Baseline Duration, Start Variance, Finish Variance, Duration Variance* (two-line headers, 104px, filterable — dates / numbers —, in the Excel export with real dates and a `+0" days";-0" days";0" days"` number format; the cell tooltips name the baseline). The task dialog shows a read-only line under the actual dates: `Baseline 07.09.2026 – 11.09.2026 · Start variance +1 day · Finish variance +2 days`, live while you type.

**Actual dates ARE the schedule** (`applyActualDates(t)`): recording an **Actual Start** sets `startDate` to it, and a task that has not finished keeps its duration, so its **Finish moves with it** (`finishFor(start, duration)`); an **Actual Finish** sets `endDate` to it. So Start/Finish already say what really happened and **dependencies need no special lookup any more**: successors are scheduled from `pred.startDate/endDate` like from any other task (the dependency arrows in the Gantt leave from the bar's end again). Editing Start / Finish / Duration of a started or finished task edits its actual dates too (`commitInlineEdit`), and in the dialog the Start/Finish inputs and the Actual inputs are kept in step live (`onActualStartChange`, `onActualFinishChange`, `onTaskStartChange`, …; saving ends in `applyActualDates()`). Clearing an actual date leaves the schedule where it was. The baseline is never touched by any of this.
- **Plans from before this model** kept their actual dates *beside* Start/Finish. Nothing is migrated or moved when such a plan is opened (an explicit user requirement: baselining is manual and the plan must not change under you). The Baseline dialog lists how many tasks have an actual date that is not in the schedule yet (`actualsNotApplied()`) and offers **Apply actual dates to the schedule** (`applyActualsToSchedule()`, with Undo): set a baseline first if you want to keep the plan, then apply. Until then `linkStart()/linkEnd()` still read such a task's actual dates for its successors (a running one projected from its real start), so their scheduling is unchanged; once applied they are equal to Start/Finish.
- **Not done (differences from MS Project)**: a task that is still running keeps its planned duration instead of being rescheduled from a status date; only Baseline 0's variances exist in MS Project, here they follow whichever baseline is compared; no per-baseline columns (Baseline 1 Start …) — pick the baseline instead; the Excel Gantt sheet does not draw baselines.

**Recording an Actual Finish completes the task** (`recordActualFinish(t, previousFinish)`, as MS Project does): `progress = 100`, and an empty Actual Start is filled with the planned start (or the finish itself if that would be later). It only fires when the Actual Finish is *new or changed* — editing % complete afterwards, or re-saving the dialog with the same finish, leaves everything alone; summary tasks are excluded (their actual dates are rollups); milestones (actual finish = actual start) complete the same way. It runs from the inline edit (toast "Actual Finish recorded — marked 100% complete") and from `saveTaskFromModal()`; in the dialog `onActualFinishChange()` / `onActualStartChange()` show the effect live in the % complete / Actual Start inputs. Clearing an Actual Finish does **not** reset % complete.

**A task that has started or finished is history and is not rescheduled** (`isStarted(t)` = it has an Actual Start or Actual Finish; an explicit user answer to "should the regular date or the actual date be auto-scheduled?": the *regular* dates are what scheduling moves, the actual dates are facts and are never touched by it — and once something has actually happened, its planned dates stop following its predecessors). So `cascadeSchedule()`, `applyConstraints()` and `rescheduleAsAuto()` skip a started/finished task (its own successors keep reading its actual dates through `linkStart/linkEnd`, so they are unaffected; the cascade doesn't propagate through it). `scheduleMismatch()` now also covers it: if its predecessors say it couldn't have started before a date later than its real start, it gets the warning triangle ("Started before its predecessors allow — they say no earlier than …") and the bar's amber ring, instead of being silently moved. The user can still edit its planned dates by hand, and clearing its actual dates makes it a normal Auto task again (it is placed by its links the next time a predecessor changes). A *manual* task is skipped as before. Not done: MS Project would also reschedule the *remaining* work of a partly-done task; here a started task's plan simply stays put.

**Triggers:** recording or editing an actual date in the list calls `applyActualDates()` then `cascadeSchedule(id)`; saving the task dialog already ends in `applyConstraints()`, which cascades. `normalizeData()` and merges don't cascade or overwrite anything. The critical path (`computeCriticalPath()`, durations only) is unchanged.

**Editors** — "handled like the normal date fields": an actual date (and a custom *Date* field) uses the very same in-list editor as Start/Finish: `dateEditor()` gives an **auto** task the native date input and a **manual** task the typed box + calendar button (`inlineTextDateHtml`, placeholder `dd.mm.yyyy`), which accepts `18.09.2026` or `2026-09-18`. The one difference is deliberate: **Start/Finish of a manual task may be free text ("TBD"), an actual date may not** — it has really happened — so anything that isn't a date is refused with a toast. An Actual Finish before the Actual Start is refused as before.

**The column system.** `TASK_COLS` is the registry for the task list — **the same list in the Tasks view and, left of the chart, in the Gantt view**: `label`, CSS grid `width`, `dflt` (shown until the user says otherwise) and `locked` (Task Name can't be hidden). Its insertion order is `DEFAULT_COL_ORDER`. **Task Mode's header**: the column used to be a bare 24px icon column with only a funnel in its header (its name just a tooltip); in the Tasks view it is now 98px wide with a real "Task Mode" header (the icon sits left-aligned under the label), while the Gantt side list keeps the 24px icon column, where there is no room for a label (`colHeadHtml(full ? 'Task Mode' : '', 'mode')`). **Shown by default: Mode, WBS, Name, Start, Finish, Duration, %, Predecessors; hidden: Actual Start, Actual Finish, Remaining Duration, Status, Resource.** (WBS was hidden at first and made a default at the user's request — see `COLS_REV` below.) The ID column is always first and the row actions always last. `renderGrid()` builds each row's cells into an object keyed by column id and joins them in `visibleTaskCols()` order, and sets the grid template as the CSS variable `--task-cols` on `#main` (`.main.view-tasks .grid-header, .grid-row` read it) — so a header, its filter button and its cells can never disagree.

The **Columns** button (toolbar, Tasks view only) opens `#columnsMenu`: a tick per column, ▲▼ arrows that move a column within the full list (hidden ones included, so the list you see *is* the order), a locked Task Name, and "Reset to default". `toggleColumn`/`moveColumn`/`resetColumns` update `colOrder`/`colHidden`, `save()` and re-render both the list and the menu. The choice is a **per-device preference** stored in `milestone-prefs` as `cols: { order, hidden }` — it is *not* part of a plan, so it isn't synced or exported, and it applies to every plan. **Making a column shown-by-default later needs a migration**, because every install's saved choice already lists it as hidden (the defaults are written by its first `save()`): bump `COLS_REV` and list the column in `COLS_REV_SHOWN[rev]`; `loadPrefs()` then unhides it **once** for anyone whose stored `cols.rev` is older (revision 1 = WBS). A column hidden again afterwards stays hidden, since the stored revision is then current. `loadPrefs()` is forgiving: unknown ids are dropped, Task Name is never hidden, and a column the saved prefs don't know yet (added by a later version) is appended and follows its own `dflt` — so shipping a new optional column never changes what an existing user sees. Because the menu re-renders on every click, the outside-click handler checks `e.target.isConnected` (same trap as the filter panel).

**Editing**: click a Resource cell (any task, groups included) for a text editor, an Actual Start/Finish cell (not groups) for a native date editor — blank clears it. WBS, Remaining Duration and Status are computed, so they have no editor. All three stored fields are in `syncPayload()`, so they are exported, backed up, synced to the plan's file and merged by the normal last-write-wins on `updatedAt`. All seven new columns are filterable (`FILTER_COLS`: WBS/Resource text, Actual Start/Finish date, Remaining number, Status list ordered Late → On Schedule → Future Task → Complete via `STATUS_ORDER`).

### Column filters

Excel-style filters on every data column, an explicit user request (first Start/Finish — "similar like if I filter a date column in Excel" — then "also good filters for the other columns"). A funnel button sits in each header in both views (`colHeadHtml()`; the compact Gantt list has the four columns it shows) and opens `#filterMenu`. The panel is **type-driven**: `FILTER_COLS` gives each column a `kind`, and the kind picks the rule set (`rulesFor(kind)`) and the list:

| column | kind | rules | list |
|---|---|---|---|
| Start, Finish | `date` | `DATE_RULES`: Equals / Before / After / Between, and Today, Tomorrow, Yesterday, This/Next/Last week, month, quarter, year, Year to date | Year › Month › Day tree |
| Task Name, Predecessors | `text` | `TEXT_RULES`: Equals, Does not equal, Begins with, Ends with, Contains, Does not contain (case-insensitive) | flat, sorted (natural order) |
| Duration, % | `number` | `NUMBER_RULES`: =, ≠, >, ≥, <, ≤, Between (either order) | flat, sorted numerically |
| Task Mode | `list` | none | the two modes |

Every list has a search box, `(Select All)` and — when some task has no value — `(Blanks)`. OK / Cancel, and "Clear filter" at the top.

- **State** (`colFilters`, one slot per `FILTER_COLS` key, made by `newColFilters()`) is *view state, like the selection*: in memory only — not in the plan data, not synced, gone on reload, and cleared by `resetTransientUI()` when the plan is switched. A `spec` is `{ type: 'rule', rule, a, b }` or `{ type: 'values', values: Set, blanks }`. The panel edits a **draft** (`filterDraft`); nothing applies until OK, and a selection that is "everything" applies no filter.
- **Evaluation** (`filterColValue`, `specMatches`, `ruleRange`): rows are filtered by what they *display* — dates via `effectiveDates()` (a summary uses its roll-up), Duration and % exactly as the grid cells compute them, Predecessors via `predecessorLabel()` (the very string the column shows, shared with `renderGrid()`). A task with no real value — a manual task with a free-text "TBD" date or duration, no predecessors — is a **blank**. As in Excel, a *positive* rule never matches a blank (date rules, text Equals/Contains/Begins/Ends, number =,>,<…), while the *negative* ones (Does not equal, Does not contain, number ≠) keep blanks; only `(Blanks)` in the list selects them on purpose. A task name can never be empty (`normalizeData` makes it "Untitled Task"), so Task Name has no `(Blanks)`. Weeks run Monday–Sunday like the calendar-week scale; relative rules are evaluated against today each render, so "this week" moves on by itself. All columns combine with **AND**, and each column's list is **cascaded**: it only offers values of tasks that every *other* column's filter lets through.
- **Hierarchy**: `filterShows(t)` = the task passes **or** any descendant shows, so a matching sub-task keeps its summary for context while non-matching siblings are hidden (memoised per render in `_filterShow`, cleared by `resetEffectiveCache()`). `visibleTaskList()` skips hidden tasks and — while any filter is on — ignores `collapsed`, so matches inside a collapsed group are visible; the chevron then shows "open" and `toggleCollapse()` just toasts ("Groups stay open while a filter is on") instead of changing anything. The stored `collapsed` flags are never touched, so clearing the filter restores the outline exactly.
- **Pinned rows** (`filterPinned`): a task you add (`addTask`), edit in the dialog (`saveTaskFromModal`) or inline (`commitInlineEdit`) stays visible even if it no longer matches — otherwise a new task (dated today) or an edited date would vanish under your cursor. Applying or clearing a filter empties the set.
- **Tree defaults** (an explicit user request): **years open, months collapsed** — opening the panel shows `2026 › September, October, …` and you open a month only to pick individual days; a whole month or year can be ticked without opening it, and a re-opened panel always starts from this default (`filterDraft.expanded` holds only the year keys). Search is the exception and shows whatever it needs. The expand arrows re-render the list, which detaches the clicked button *before* the document's outside-click handler runs — that handler therefore checks `e.target.isConnected`, or the panel would close on every expand/collapse.
- **Search** works like Excel's: typing selects exactly the matches (`(Select All Search Results)`), clearing it restores the previous selection; it matches the date as shown (`07.09.2026`), the month name and the year. Ticking a date while a rule is chosen switches the panel back to a list filter. **Escape in a `type=search` input clears it and fires an `input` event after our own Escape handler has closed the panel**, so the panel's event handlers all guard on `filterDraft` being null.
- **Feedback**: funnels rest at 55% opacity and only the funnel under the pointer highlights (there is deliberately **no header-wide hover** that brightens every funnel at once — it looked like the whole header was interactive); an active column's funnel is always highlighted in the accent colour (tooltip: "Filtered: …"); `#filterBar` in the toolbar shows a chip per filter (× removes it), "N of M tasks" and "Clear all"; an empty result shows "No tasks match the filter" (list and chart) with a Clear button.
- **Layout**: the Duration and % columns were widened (96px / 54px) so their labels aren't cut off by the funnel. (The Gantt view's list is the same list, so it has every funnel too; the old compact list omitted the buttons for columns it didn't show, but their filters still apply and keep their chip.
- Not built (deliberately, to keep it a *filter*): sorting from the header menu, and Excel's compound "Custom Filter… (and/or)". Between covers the common range case.

### Excel export

**Data → Export to Excel…** (an explicit user request: "well formatted") writes a real `.xlsx`, **hand-built with no library** — the app has no dependencies, and SheetJS's free build can't write styles anyway. An `.xlsx` is a ZIP of XML parts, so the module (`/* Excel export */`, before "Local backups") has four small pieces: `zipStore()` (a ZIP writer with CRC-32; entries are *stored*, not deflated — the files are small), `xlsxStyleBook()` (dedupes fonts/fills/borders/number formats into `styles.xml`; `style({...})` returns a cell-format index), `xlsxSharedStrings()`, and `xlsxSheet()` (rows/cells/merges/columns/data bar/print setup → worksheet XML). `buildXlsx({ scope, gantt })` assembles the package and returns a Blob; `downloadBlob()` saves it as `<plan name>-<date>.xlsx`. The dialog (`#excelModalBg`) offers **which tasks** — shown only when a column filter is on: all, or only those matching it (`exportTaskRows(scope)` uses `filterShows`) — and **Add a Gantt chart sheet**.

- **Tasks sheet**: title + subtitle rows, then **ID, then the *Tasks view's* visible columns in its order** (`visibleTaskCols('tasks')` — the sheet follows the Tasks view's own choice wherever the export is started from; the dialog's *Columns* choice: "As shown in the task list" — the default — or "All columns", in the default order; `XCOLS` maps each to a header and width, and the freeze pane, autofilter range and % data bar all follow the columns actually present) — the values the grid *displays* (same rules as `renderGrid()`: an automatic group shows its roll-up, a manual task its own dates, free-text "TBD" dates/durations are kept as text, `predecessorLabel()` for the references). Dates are **real Excel dates** (`xlsxSerial` = `dayNumber + 25569`, format `dd\.mm\.yyyy`), Duration a number with format `[=1]0" day";0" days"`, % a fraction with `0%` plus a **data bar**. The outline is exported in full, ignoring collapsed groups; indent = depth, groups bold on a light fill, milestones prefixed `◆`. Dark header row, thin light borders, a standard 19pt row height, **frozen panes** (header + everything up to Task Name), autofilter, landscape A4 fit-to-width, header row repeated on every printed page, page-number footer, coloured tab, gridlines off.
- **Gantt sheet** (skipped when nothing is scheduled): **ID and the *Gantt view's* visible columns in its order** (`visibleTaskCols('gantt')` — an explicit user request: each sheet follows the column choice of its own view; by default Mode, WBS, Name, Start, Finish, Duration, Baseline Start/Finish, Duration Variance; "All columns" widens the Tasks sheet only) written by the same `writeTaskRow()` as the Tasks sheet (values, formats, indent, group styling), frozen through Task Name like the Tasks sheet, the title/subtitle merged across the list columns, then **one column per ISO calendar week** (Monday–Sunday, like the app's Week scale) — months merged in the top header row, `CW n` rotated 90° below, this week's header highlighted amber; **solid = done, light = still to do, dark = group, ◆ = milestone**. A cell is solid when the bar's done portion (`Math.round(duration × progress / 100)` days) reaches into that week. Bar colours are the light theme's palette as hex (`XLSX_COLORS`, `statusColorHex()` mirrors `statusColorVar()` — complete/overdue/in-progress/not-started, or the task's own colour). Projects longer than 170 weeks switch to **one column per month** (year above, month name below). Covered by `verify_excel_views.py` (two views with different columns, order, 'all columns', defaults, and the dialog's download).
- **Header colour**: every header cell — the Tasks sheet's column headers, and on the Gantt sheet the ID/Name/Start/Finish headers, the month band and the week columns (except "this week", which keeps its yellow highlight) — is **Midnight Blue, PANTONE 281 C, `#00205B`** with bold white text (`HEAD_FILL` in `buildXlsx`; an explicit user request, given as a brand-colour swatch). `HEAD` (`24292F`, dark grey) is *not* a header colour any more: it is only the colour of summary bars on the Gantt sheet.
- **Column widths**: `XCOLS` gives each column's Excel width in character units; **WBS is 15** — the app's fixed 104px WBS column at about 7px per unit, enough for eight levels (`2.2.2.2.2.2.2.2`) — on the Tasks sheet and in the Gantt sheet's list part alike (`verify_milestone_tbd.py` reads the widths back with openpyxl). The print layout's WBS column is 66 units for the same reason.
- **Text is never a formula**: every string goes in as a shared string (`t="s"`), so a task called `=1+1` stays text. Cell text is cut at Excel's 32,767-character limit and control characters XML forbids are stripped (`xmlEsc`), or Excel refuses the file.
- **Excel is stricter than the tools available here.** It was verified by loading the files in openpyxl and by checks on the package itself (ZIP CRCs, well-formed XML, content types and relationships resolve, style/string indexes in range, rows and cells ascending, dimension and merge counts, worksheet elements in **schema order** — Excel rejects a misordered sheet that openpyxl accepts), but **not opened in Excel itself**. If Excel ever says it "found a problem with some content", the suspects are the worksheet element order, `styles.xml` counts, and the data-bar rule.

### Collapse all / Expand all (a multi-step cycle)

**One toggle button in the header cell of the ID column** (`#collapseToggleBtn`, `.id-toggle`) — directly above the first task, in both views (the same list). It was two toolbar buttons first, then one collapse/expand toggle, and is now (by the user's request) a **cycle through the outline levels**: everything open → *collapse all* → open the **first level** of groups → the **next level** → … → everything open → around again. Level `L` means "groups nested fewer than `L` deep are open, deeper ones are closed", so `L = 0` is all collapsed and `L = levels` (the depth of the deepest group + 1) is all expanded. `collapseState()` works out which level the stored flags currently match (every depth below the deepest group contains a group, so each level is a distinct state), and `toggleAllCollapsed()` moves to `next`: `L + 1`, wrapping from fully open back to `0`. **A state the cycle can't produce** (one group opened or closed by hand) has `current === null` and the next click goes to *Collapse all*. Only groups are touched (`groupTasks()`); leaves keep their flag.

The icon and title show what the next click does: `angles-up` "Collapse all groups", then `angles-down` "Expand to level 1", "Expand to level 2", …, "Expand all groups" for the last step. The state is **derived from the stored `collapsed` flags**, so it survives a reload mid-cycle. Because `renderGrid()` rebuilds the header on every render, `updateCollapseButtons()` (called from `render()` after `renderGrid()`) re-applies icon, title and disabled state each time. Like the arrow on a single group (`toggleCollapse`) this is **view state and is deliberately not stamped with `updatedAt`** — a collapse must not travel to another device as if it were an edit. It is disabled when there are no groups, and **while a column filter is on**, because the filtered list shows every group open (see Column filters); the title says so, and calling `toggleAllCollapsed()` anyway just toasts.

### Drag-and-drop reordering, and Escape

Tasks are reordered by dragging **anywhere on the row** (the `.grid-row` itself is the `draggable` element — an explicit user request, after an earlier ID-cell-only handle), so clicks on cells, inline editing and double-click still work because a click that doesn't move never becomes a drag. The row shows the normal pointer at rest; the `grabbing` cursor only appears once the mouse has been held down on it for `GRAB_HOLD_MS` (250 ms) — `wireGrabCursor()` adds a `.grabbing` class after that delay and clears it on mouseup/dragstart. A plain CSS `:active` rule was deliberately not used: it flashes the grab cursor on every ordinary click, and a permanent `cursor: grab` made every row look like a drag handle. **The one exception is the row currently being edited**: `renderGrid()` renders it `draggable="false"`, because a draggable ancestor stops the mouse from selecting text inside an `<input>`; it turns draggable again on the next render after the edit. Clicking an editable cell (Start/Finish/Duration/Predecessors/Name) starts an inline edit and deliberately doesn't select the row (unchanged behaviour); every row is a drop target, in both Task view and Gantt view's label pane. The top half of a row means *insert before it*; the bottom half means *insert after it*, **except** that "after" an *expanded summary* is the slot directly beneath its header, i.e. its first sub-task (shaded `.drop-into`), since that's where the eye reads it. Dropping in the blank area below the last row moves the task to the end of the top level. The task takes the target's parent, so this both reorders and moves between groups; a summary always travels with its subtree (children reference it by `parentId`). A task can't be dropped onto itself or anywhere inside its own subtree (`canDropTaskOn()`) — that would create a `parentId` cycle.

Drop indicators (`.drop-before/-after/-into/-end`, `.dragging`) are classes toggled directly on the live row, **never a `render()`** — replacing the DOM mid-drag cancels the browser's drag. `moveTask(id, targetId, zone)` renumbers the destination level `0..n` (and the source level if the parent changed) and stamps `updatedAt` only on tasks whose `order`/`parentId` actually changed — `order` is a merged field, so an un-stamped renumber would never reach another device, and stamping everything would make untouched tasks look freshly edited. A drop that lands the task back where it started is a no-op (no save). Predecessor links are by internal id, so they survive a move; only the displayed `#` numbers (outline position) change.

**Escape** (the global handler in `wireGlobalEvents()`) closes any open dialog/menu first; only when none was open, and the key didn't come from a text field, does it clear `selectedTaskId`. It checks `e.target`, *not* `document.activeElement`: an inline editor's own Escape handler re-renders and destroys the focused input before the global handler runs, so `activeElement` is already `<body>` and would wrongly count as "not typing" — cancelling an edit used to deselect the row too. A related race: an inline editor only receives focus a frame after it appears, so an Escape in that instant lands on the page — the handler therefore also cancels any open inline edit itself (`if (!overlayOpen && editingCell) cancelInlineEdit()`) instead of clearing the selection and leaving the editor open. (This surfaced as an intermittent test failure: Playwright presses the key the moment the input exists.)

### Confirm dialog buttons

`openConfirmModal({ title, body, action, confirmLabel, confirmClass })` is shared by every confirmation. Its action button defaults to `btn btn-primary btn-danger`, which `.btn-primary.btn-danger` renders as a **filled red** button (white text, stays red on hover) — used by Delete task and Delete plan. A non-destructive caller passes `confirmClass`: Restore backup uses `btn btn-primary` (green — it replaces data after a safety download, but isn't a delete) and Disconnect file uses plain `btn` (an explicit request: no green button there). The default used to render green with red text, because `.btn-primary`'s background beat `.btn-danger`'s colour-only rule. Also: `restoreBackup()` closes the Backups dialog *before* opening the confirmation — the confirm dialog comes earlier in the page, so it used to open behind the Backups dialog and could not be clicked.

### Task constraints

`CONSTRAINT_TYPES` ports Microsoft Project's 8 primary constraint types (ASAP/ALAP/MSO/MFO/SNET/SNLT/FNET/FNLT), each entry carrying `hasDate`, `basis` (`'start'` or `'finish'` — which of the task's own dates the constraint date binds), and `bound` (`'lower'`, `'upper'`, or `'exact'`). A task stores `constraintType` (default `'ASAP'`) and `constraintDate` (`null` unless `hasDate`).

How each `bound` interacts with the forward-only cascade above is the crux of this port, since Milestone has no bidirectional scheduler to fully enforce an upper bound or a true backward ALAP pass:

- **`lower`** (SNET/FNET) and **`exact`** (MSO/MFO) fold directly into `constraintStart(task)` as one more candidate alongside every predecessor's own earliest-start push — whichever candidate is latest wins, the same mechanism that already resolves multiple predecessors against each other. This is why an MSO/SNET date can still end up pushed later than the pin: a predecessor genuinely demanding a later start always wins, exactly like real MS Project's own "meet as many constraints as possible" behavior when a schedule is over-constrained.
- **`exact`** additionally gets pinned immediately in `saveTaskFromModal()` the moment the constraint is set (the task's stored dates are set to the constraint date right then, preserving duration) — this is what makes "Must Start/Finish On" actually *move* a task instead of merely capping it, the one behavior `constraintStart()`'s lower-bound treatment alone wouldn't produce.
- **`upper`** (SNLT/FNLT) is deliberately **not** enforced by the cascade at all — this app's scheduling engine places a task at the *earliest* date its links and lower-bound constraints allow (see `placeByLinks()`), so there is no code path that could honor an upper bound without a backward pass. Instead, `constraintViolated(task)` checks whether the task's *current* dates still satisfy its constraint (exact: date must match exactly; upper: current date must not exceed it) and the grid surfaces a mismatch via a small calendar icon next to the task name, turning `--danger`-colored when violated — the same "surface it, don't silently override a deliberate placement" stance already established for a manual placement ahead of a predecessor. Real MS Project does the same thing here: an over-constrained schedule gets a conflict indicator, not a silent reversal of whichever constraint lost.
- **ALAP** is treated identically to ASAP for actual date computation in this version — both are lower-bounded only by predecessors, with no backward slack-filling pass. A true ALAP (schedule as late as possible without delaying a successor) would need the same latest-start machinery `computeCriticalPath()` already computes for leaf tasks, just applied continuously rather than only behind the critical-path toggle; deferred as a genuine v1 scope cut rather than built halfway. No violation warning is shown for ALAP since there's nothing here to violate yet.

### Gantt rendering

Position math is plain day-number arithmetic (`dayNumber()`/`dayNumberToIso()`, UTC-based via `Date.UTC()`) rather than local-time `Date` arithmetic — the same reasoning Pulse's own Dashboard Gantt chart uses: two devices in different timezones must compute the identical pixel position from the same ISO date string, which a local-time parse doesn't reliably guarantee across a DST boundary. Display-facing formatting (`fmtDate()`/`fmtDateY()`) still parses as local time, matching how every other date renders in this app. `fmtDate()` (used everywhere task/Gantt dates and the week-level Gantt ticks are shown) renders as fixed `DD.MM.YYYY` rather than a `toLocaleDateString()` locale format — an explicit user request to match a traditional planner's date style regardless of browser locale; `fmtDateY()` (About dialog only) is unchanged.

The grid pane (task table) and the Gantt pane share one implicit vertical scroll position: the grid's own row list is `overflow: hidden` (never user-scrollable directly) and its `scrollTop` is driven programmatically from the Gantt pane's real scroll container, with wheel events over the grid forwarded into the Gantt pane's scroll instead (`wireScrollSync()`). This works because CSS `overflow: hidden` still permits *programmatic* `scrollTop` — it only suppresses the scrollbar UI and user-initiated wheel/touch scrolling — so the two panes' rows stay pixel-aligned with only one real scrollable element.

**The Gantt view's left side is the same full task list as the Tasks view** (an explicit user request: "bring the task list view to Gantt as well (left part, not the Gantt)"; it used to be a compact ID/Mode/Name/Start/Finish sidebar with its own 32px header and no editing). One `renderGrid()` builds it for both views (`full` is always true — the flag remains only as a marker), so the columns (the **Columns** button is available in both views), the funnel filters, the collapse toggle, WBS, the row actions (Edit / Clone / Delete), inline editing, drag-to-reorder, column lines, frozen columns and sideways scrolling all work in the Gantt view exactly as in the Tasks view; the CSS list rules are scoped to `.main` (not `.main.view-tasks`). What differs in the Gantt view:
- **Its own set of columns** (an explicit user request: "the columns shown in the Gantt view should save a separate set"): the two views share the *columns to choose from* (`TASK_COLS`) but each keeps its own order and visibility. `colOrder` / `colHidden` are the **Tasks view's** set (unchanged, saved as `cols`); `gColOrder` / `gColHidden` are the **Gantt view's** (saved as `gcols` in `milestone-prefs`, per device like everything in there). `viewColOrder(view)` / `viewColHidden(view)` pick the set of a view (default: the current one) and `visibleTaskCols(view = currentView)` is what `renderGrid()`, `updateFrozenColumns()`, the Columns menu and the Excel export's "as shown" all use, so each of them follows the view you are in. The Gantt default (taken from the user's own Columns-menu choice) is `GANTT_DEFAULT_ORDER` — the Tasks view's order with Duration moved in front of the actual dates: Mode, WBS, Name, Start, Finish, Duration, Actual Start/Finish, %, Predecessors, Remaining, Status, Baseline Start/Finish/Duration, Start/Finish/Duration Variance, Resource, the custom fields — with `GANTT_DEFAULT_SHOWN = Mode, WBS, Name, Start, Finish, Duration, Baseline Start, Baseline Finish, Duration Variance` ticked, and loading follows the Tasks set's rules (a column the save doesn't know yet is appended hidden; Task Name is never hidden; garbage is dropped); preferences saved before this existed have no `gcols` and so give the Gantt view that default while the Tasks view keeps its choice. The **Columns** menu edits the set of the view you are in (`Columns · Gantt view`, with a hint that the other view keeps its own choice), *Reset to default* resets only that view's set, and switching views closes the menu. Filters are shared (`colFilters`): a filter on a column the current list doesn't show still filters, and keeps its chip. The frozen columns and the minimum list width follow the set (`updateFrozenColumns()`). Covered by `verify_gantt_columns.py`.
- **Layout**: the list is a fixed-width pane (`--grid-pane-width`) with the chart to its right; the Tasks view's list fills the window and the chart pane is hidden (the only `.main.view-tasks` rules left: list `flex: 1`, hide the chart, hide the resize handle).
- **Same header height**: `--head-h` (42px, `HEAD_H` in JS) is the height of the list header *and* the chart's timescale (`.gantt-header`), and `svg.gantt-deps { top: var(--head-h) }` — so rows stay level (they used to be 32px in both; the list's two-line headers need 42). The link-drag preview subtracts `HEAD_H`.
- **Scrolling**: vertically the *chart* drives the list (`wireScrollSync()`: chart `scroll` → `gridRows.scrollTop`; a wheel gesture over the list is forwarded to the chart, unless it is mostly sideways); horizontally the list scrolls by itself — `.main.view-gantt .grid-rows { overflow-x: scroll }` (a permanent track, like the chart's own scrollbar, so both panes end at the same height); the header follows via `syncHeaderScroll()`; the frozen columns (ID … Task Name) stay put.
- **Width**: a resizable per-device preference `gridPaneWidth` (default **640px**, was 400; `GRID_PANE_REV = 1` — a width saved by the earlier sidebar is not kept), dragged with `#gridResizeHandle` (a thin strip on the pane's right edge, Gantt view only; live via `--grid-pane-width`, saved on mouseup). It is clamped to `[max(320, frozen columns + 60px), min(1800, window − 240px)]` (`minGridPaneWidth()`, `applyGridPaneWidth()`, also re-applied on window resize and after every render; `frozenMinWidth` is set by `updateFrozenColumns()`), so the frozen columns never fill the whole list and the chart never disappears.
Covered by `verify_gantt_list.py`.

Bar color (`statusColorVar()`) is either the task's own explicit `color` override, or derived from status: complete (100%) → `--status-complete`, overdue (end date in the past, not complete) → `--danger`, in-progress (progress > 0) → `--accent`, otherwise `--status-not-started`. A bar's unfilled portion is `color-mix(in srgb, var(--bar-color) 22%, var(--panel))` and its progress fill is the solid color — this is why the fixed palette only needs one solid hex per token rather than Pulse's paired solid/`-bg` tokens.

**Timescale** (`ZOOMS`: Week 14 px/day, Month 5, Year 1.5; the tabs in the top bar are generated from it). **Year is the default** (`DEFAULT_ZOOM`, an explicit user request), and the **Day scale was removed** at the user's request (a saved `'day'` falls back to Year). Every header tick spans its whole period — `renderGanttHeaderTicks()` returns `{ left, width, html|label, title, … }` and `renderGantt()` clips a tick that begins before the chart (the week/month/quarter holding the first day) to the left edge; `.gantt-tick` is `overflow: hidden` so a label is truncated, never spilled into the next tick. Ticks carry a `zoom-<id>` class. The header is always one row (`--row-h`) tall.

- **Saved scale and the one-time reset**: `prefsPayload()` stores `zoomRev: ZOOM_DEFAULT_REV` next to `zoom`, and `loadPrefs()` only honours a saved zoom whose `zoomRev` matches — otherwise it uses `DEFAULT_ZOOM`. This is deliberate: the previous default (Week) had been written to every install's prefs by its very first `save()`, so a plain change of the default would never have been seen by anyone who'd already opened the app. Bump `ZOOM_DEFAULT_REV` to reset everybody's scale once again; a scale chosen afterwards is remembered as usual.
- **Week**: **calendar weeks** (an explicit user request; the scale used to be labelled with each Monday's date). One tick per ISO 8601 week — weeks start on Monday, week 1 holds the year's first Thursday — labelled `CW 37` over the Monday's date (`07.09.`; the full `04.01.2027` on the first tick and wherever the year changes), with a tooltip giving the whole week (`CW 37: 07.09.2026 – 13.09.2026`). `isoWeekOf(dayNumber)` does the arithmetic on UTC day numbers (day 0, 1970-01-01, was a Thursday) and returns `{ week, year, monday }`; note the week's year can differ from its Monday's year (29.12.2025 is CW 1 of 2026). The prefix is the constant `CAL_WEEK_LABEL` (`'CW'`; German users may prefer `'KW'`).
- **Month**: one tick per month, `Sep 2026`, as wide as the month has days.
- **Year** (added by request): one tick per **quarter** — the year in bold on each Q1 (and on the first tick), `Q1`–`Q4` below it, a heavier left border (`.year-start`) at each year boundary. At 1.5 px/day a quarter is ~137px. Bars keep their 6px minimum width, and dragging/resizing rounds to whole days (`Math.round(dx / px)`), so 30px is 20 days.
- **Dependency arrows** used to be drawn one header-height (32px) too high, from the very first version: the `<svg>` overlay was `top: 0` of `.gantt-content`, but its y-axis (`barGeom`, the link-drag preview's `- ROW_H`) starts at the first row, i.e. below the sticky header. It is now `top: var(--row-h)`.

Dependency arrows are a single `<svg>` overlay (`#ganttDeps`) redrawn each render, one elbow-routed `<path>` per predecessor link between two currently-visible tasks (a link to/from a task hidden behind a collapsed ancestor is simply not drawn). Drag-to-link (the small circle handle on a bar's right edge) draws a temporary dashed preview path during the drag and resolves the drop target via `document.elementFromPoint()` against `data-row-id`/`data-id` attributes on the row background and bar elements.

**Baseline under the bars (Tracking Gantt).** The bar is the *current schedule* — for a started task that already IS where it really began and ended (see "Baselines, actual dates and variance") — and the compared baseline is drawn as a thin **4px grey line** under it (`.gantt-base`, `baselineBarHtml()`, in the row's bottom strip at `ROW_H − 5`, `pointer-events: none`; a milestone gets a hollow diamond `.gantt-base-ms`; a group its rollup). The ruler button in the Gantt toolbar (`#baselineBtn`, `showBaseline`, a per-device preference stored in `milestone-prefs`, default on) hides it; its tooltip names the compared baseline. The bar's tooltip gets `Baseline: 07.09.2026 – 11.09.2026 (start +1 day, finish +2 days)` (`baselineNote()`). `computeDateRange()` includes the baseline dates so the line can never fall outside the chart. Dependency arrows leave from the end of the bar (no special anchor); the earlier "actual span" bars, the dotted projection and the arrow anchors were removed with this change. A manual group's rollup bar (`.gantt-rollup`) uses the same strip and can be overdrawn. Not drawn on the Excel Gantt sheet. Covered by `verify_baseline.py`.

### Fixed color palette (GitHub, dark-first)

Milestone originally ported Pulse's full switchable theme system — a light/dark toggle crossed with 5 color schemes (Standard, Modern/VS Code, Dracula/Alucard, GitHub, GitHub Dark Dimmed), each its own `[data-theme]`/`[data-scheme]` CSS block plus a palette-picker dropdown and `THEME_SCHEMES` array driving it. The 5-scheme picker was removed by explicit request in favor of always looking like GitHub — no `data-scheme` attribute, no picker UI, no `THEME_SCHEMES` array. The plain light/dark toggle came back afterward (also by request): `:root` is GitHub's Dark Dimmed palette (the default — `theme` starts `'dark'`, matching the "GitHub Dimmed by default" request), and `html[data-theme="light"]` overrides it with GitHub's own light palette — the inverse of the usual "light is `:root`, dark is the override" pattern, since dark is what's meant to be seen first here. `toggleTheme()`/`applyTheme()`/`updateThemeToggleUI()` are otherwise the same shape Pulse's own toggle uses. `.btn-primary` uses `--task-green` instead of `--accent` in both modes, matching GitHub's actual green primary-button convention (previously a github/githubdimmed-only override, now just the default regardless of light/dark).

### Native controls follow the theme (`color-scheme`)

`:root` sets `color-scheme: light` and `html[data-theme="dark"]` sets `color-scheme: dark`. That property is what tells the browser how to draw **its own** controls: the date picker's calendar icon *and* its popup, `<select>` menus, checkboxes, number spinners and scrollbars. Without it they are always drawn for a light page — the calendar icon in every date field was **black on the dark theme** (measured: contrast ≈ 39/255; ≈ 216 now). It is deliberately global rather than only on `input[type=date]`, so every date field is covered (task dialog, constraint date, actual dates, the inline list editor, the filter panel's date rules). `verify_dark_controls.py`-style checks screenshot a date field and measure the icon's ink against the field's background, since the native popup itself can't be captured headlessly.

### Top bar matches Pulse (and nothing else does)

By explicit user request the **top bar only** follows Pulse's look — a broader restyle of the whole app was tried and reverted because only the bar was wanted. It uses Pulse's values (read from `../Pulse/pulse.html`): `gap: 14px; padding: 0 16px`, brand `21px / 700 / -0.02em` with a 26px logo, the plan switcher (`.plan-btn`: the plan name, borderless and dim, background only on hover/open; 243px wide — the old name field's 182px + one third, at the user's request), `.topbar-divider` hairlines between the clusters, bordered pill `.view-tabs` with accent-coloured active text, bordered square `.icon-btn`s, and semibold `.btn`s at the browser's own 13.33px. **Every control rule is scoped to `.topbar`** (`.topbar .view-tab`, `.topbar .icon-btn`, `.topbar .btn`) precisely so the toolbar, list, dialogs and dropdowns keep their existing look — don't move these to the global `.icon-btn`/`.btn`/`.view-tab` rules. The second bar, the grid, and the modals are deliberately *not* Pulse-styled.

### Undo and redo

An explicit user request (after Auto scheduling became bidirectional, one edit can move a whole chain of tasks). **Snapshot-based and generic**: every change goes through `save()`, and `recordHistory()` (called from `save()` after `normalizeData()`) compares the plan text (`canonicalText()` — the very text written to the file: project + tasks + tombstones) with what it was after the previous save; when something other than a **timestamp** (`updatedAt`, tombstone `deletedAt` — `stateSig()` zeroes them) changed, the previous text is pushed on `undoStack` and `redoStack` is emptied. So *everything* is undoable — edits together with what the cascade moved, add / delete / clone, drag, baselines, the working calendar and holidays, plan settings — with no per-action code. Saves within `historyCoalesceMs` (300 ms, a `let` so tests can set 0) of each other belong to one gesture and share one step; at most 100 steps and 40M characters are kept. **View state is not part of it** (view, zoom, columns, filters, selection: not in the plan text).
- **Restoring is merge-safe** (`applySnapshot(text)`): a task whose content differs from the target gets the target's version with `updatedAt = now` (so a sync with another device keeps the restored state instead of undoing the undo), a task that comes back loses its tombstone, a task that goes away is tombstoned (`deletedAt = now`), and `project` is replaced (`updatedAt = now`) only when it differs (ignoring `updatedAt`). `stepHistory('undo'|'redo')` does it with `histBusy` set (so `save()` does not record it), cancels an inline edit, drops the selection if its task is gone, clears any toast Undo (a delete/clone Undo would act on a state that no longer exists) and shows `Undid: Finish of "A" and 2 other tasks` with the opposite step as the toast's button. `describeChange(before, after)` writes that label from the diff: one added/deleted task (with sub-tasks), the changed field(s) of the task you edited — the changed task none of the other changed tasks feeds, so a cascade names its cause — plus "and N other tasks", or `Plan settings`.
- **When the history is dropped** (`resetHistory()`): on load, on every plan switch (`resetTransientUI()`), and when another device's changes are merged in (`mergeFromFile()` with `changed`) — undo must never revert somebody else's work. It lives in memory only (nothing survives a reload). A toast Undo (delete, clone, baselines …) still works as before; what it does is an ordinary change that is itself a history step.
- **UI**: two icon buttons at the left of the toolbar (`#undoBtn` / `#redoBtn`, disabled when empty, tooltips show the step count; `updateUndoUI()`), and **Ctrl/Cmd+Z**, **Ctrl/Cmd+Shift+Z**, **Ctrl+Y** (ignored while typing in an input/textarea/select — the browser's own undo — and while a dialog is open).
- Covered by `verify_undo.py` (35 checks, incl. sync safety with a stale tombstone) and, in `verify_stress.py`, by `history` operations and a `roundtrip` operation (undo then redo must leave the plan unchanged) between the usual invariants.

### Data durability

Same shape as Pulse/mytasks, sized down for a single-entity (`tasks`, not items+milestones+workstreams) data model:

- **Tombstones**: `deletedTaskIds` (`{id, deletedAt}[]`). `deleteTaskFlow()` cascades to the full descendant subtree, tombstones every id, and its undo toast restores the whole subtree *and* any predecessor links that were stripped from surviving tasks pointing at the deleted set (captured before the strip, replayed on undo) — a plain "restore the deleted tasks" undo without this would silently leave a surviving task's dependency broken even after the delete itself was undone.
- **Merge** (`mergeData(data, opts)`) — **three-way and field-level when there is a base, "newer whole task wins" when there is not.** An explicit user request ("does the app support the file merge logic as Pulse? if people work in parallel on the file?" → "build it"), and deliberately a step further than Pulse's whole-record merge. The **base** is `lastSyncedSnapshot`: the text of the file as of this plan's last sync (set by `setSyncBase()`, also kept per plan in `localStorage["milestone-syncbase-<planId>"]` so offline work still merges field by field after a reload; removed when the plan is unlinked or deleted). `threeWayMerge(mine, theirs, base)` decides per field: only they changed it → take theirs; only you did → keep yours; both changed it the same → fine; both changed it **differently** → a **conflict**: the newer record's value wins (`updatedAt`; a tie is broken by comparing the two records' stable JSON, so every device picks the same winner and they converge) and the conflict is reported. So A changing a task's Start while B changes its Resource keeps both (Pulse would lose one). The **project** settings (name, working calendar, baseline metadata, custom-field names, …) merge the same way, field by field. Without a base (first link, `applyImport('merge')`, a file from before this) it falls back to the newer whole task, with no conflict reporting; a field the other side *removed* is removed here too. Tombstones are unchanged (a delete wins unless the task was edited after it; the merge also sweeps a local task whose tombstone just arrived). `opts`: `respectTombstones` (default true; `applyImport('merge')`/backup restore pass false or skip merge), `base`, `conflicts` (array to fill), `changedIds` (Map id → the fields the merge changed).
- **Write-time merge** (`writeSyncFile()`): the file is **read before it is written**. If it differs from the base (someone else wrote since), `mergeFromFile(data, 'write')` merges it in first, and the file gets the *combined* result — a save never erases another person's work. If the file already says exactly what would be written, nothing is written. **Poll** (`pollFileSync()`, every 45s and at startup): merge, set the new base, and if the merged state differs from the file (the other side's changes arrived, or this side's own edits/wins are not in the file yet) `queueFileSyncWrite()` puts the result back, so the other device gets what only this side had. No ping-pong: `canonicalText()` writes **stable JSON** (sorted keys, tasks and tombstones in id order), so two devices in the same state write the same bytes, and a device only writes when its text differs from the file.
- **After a merge the schedule is re-checked** (`replanAfterMerge()`): an Actual Start/Finish that arrived overrides Start/Finish (`applyActualDates`), then every task the merge touched goes through `applyConstraints()` (manual and started tasks are left alone), so a predecessor moved on one device moves the successor another device had edited, later or earlier. The toast says how many tasks were re-planned.
- **Sync conflicts** (Pulse-style, session-only): `syncConflictLog` (`{kind: 'task'|'plan', id, name, fields: [{key, mine, theirs, kept}]}`); `reportSyncConflicts()` shows a toast with **Review** and an amber **`N conflicts`** badge (`#syncConflictBtn`, next to the file indicator); the dialog (`#syncConflictsModalBg`) lists each conflict — field by field, yours vs the other version, which one was kept — with **Use mine / Use theirs** (applies those fields, stamps `updatedAt`, re-plans, saves, so the decision syncs), **Dismiss** and **Dismiss all**. Whether a group is folded (`collapsed`) is never a conflict. The log is cleared on a plan switch. Covered by `verify_sync.py` (two simulated devices sharing a file: write-time and poll merges, field-level merge, conflicts and their dialog, deletions vs later edits, re-planning, ping-pong, tie-break, offline edits after a reload, plan settings, first link).
- **Limits (as in the design)**: it is a file in a shared folder, not a server — there is no locking, so two writes in the same instant can still race (the second one's read-then-write window is a few milliseconds); the poll is every 45s, not live; a synced-folder service that makes "conflicted copy" files (OneDrive, Dropbox) is not detected; a field-level merge cannot know two *different* edits belong together (e.g. Start and Finish edited by different people), and the schedule re-check does not know which of two devices' hand-set dates was meant.
- **Local backups**: one rolling snapshot per calendar day *per plan* in `localStorage["milestone-backups-<planId>"]`, capped at 7, via `maybeSnapshotBackup()` called from every `save()`. Restoring a backup restores into the current plan.
- **File System Access API sync**: one file *per plan* (not Pulse's later folder/multi-file split — that split exists specifically for *concurrent multi-workstream* editing, which doesn't apply to a single-project plan). `linkNewFile()`/`linkExistingFile()` pick a `FileSystemFileHandle` via `showSaveFilePicker()`/`showOpenFilePicker({ mode: 'readwrite' })` (without `mode` a picked file only has read permission), persisted across reloads in IndexedDB (`milestone-fs`, key `plan:<id>`). Only the **current** plan is in memory, so the sync globals (`syncFileHandle`, `fileSyncStatus`, `lastSyncedSnapshot`, the poll timer) describe the current plan's file and are re-pointed on every plan switch (`activatePlanFile()`). Writes are queued (`queueFileSyncWrite()`/`fileSyncWriteInFlight`/`fileSyncWritePending`) so a burst of rapid saves collapses to the minimum necessary writes and always reflects the latest state, not a stale queued snapshot — same mechanism Pulse's own file sync uses. Background polling every 45s (`FILE_SYNC_POLL_MS`) picks up changes made by another device sharing the same file (e.g. via iCloud Drive/OneDrive/Dropbox). Linking is **mandatory** wherever the browser supports it — see "Mandatory file linking" under Plans.

### Plans

A plan is one project: its own tasks, tombstones, backups and linked file. The current plan is the only one loaded (`project`/`tasks`/`deletedTaskIds` globals are always "the current plan"); everything else about the app is unchanged. The switcher is the button at the top left (`#planMenuBtn`, replaces the old project-name input): a menu listing the plans — each with its file name or "Browser only" — plus New plan, Open file as plan, Rename, Duplicate and Delete (all acting on the current plan). New/Rename share one small dialog (`#planModalBg`); "Create with file…" opens the save picker *first*, straight from the click (it needs the user gesture), and only then creates the plan and writes its first content into the file.

**Migration** (`initPlans()`): the first time this build runs, the single pre-plans project (`milestone-v1`) becomes plan id `plan1` — copied, not moved, so the old keys are a rollback copy and, once `milestone-plans` exists, are never read again. Its theme/zoom/view/pane width seed `milestone-prefs`, its `milestone-backups` are copied to `milestone-backups-plan1`, and `_fsMigrateLegacyKey()` copies the old IndexedDB handle (`syncFile`) to `plan:plan1` exactly once (guarded by `milestone-handle-migrated`, otherwise unlinking Plan 1 would bring the file back on the next load).

**Switching** (`switchPlan(id)`), in this order: `persistLocal()` (browser copy, synchronous) → `flushFileSync()` (let the in-flight write land, then write once more) → `planEpoch++` → stop polling → load the other plan → `resetTransientUI()` (selection, inline edit, task dialog, and **any Undo toast** — an Undo for the old plan must not act on the new one) → `render()` → `activatePlanFile(true)`. The `true` matters: a switch is a click, so a linked file whose permission lapsed can be re-requested right there instead of falling back to the amber Reconnect button (a plain page load has no gesture and still shows Reconnect).

**The write race, and why `planEpoch` exists.** File I/O is async, so a write or a poll for plan A can still be in flight after the user has switched to B. `writeSyncFile()` therefore captures *both* the file handle and the payload text synchronously, before its first `await` — an in-flight write always puts A's data into A's file, never B's — and every async sync function (`writeSyncFile`, `pollFileSync`, `reconnectFile`, `finishLinking`, `activatePlanFile`) compares `planEpoch` after each `await` and drops its result if the plan changed. Without that, a poll that was waiting on A's file would `mergeData()` A's tasks into B. The Playwright tests cover both (edit + switch in the same tick, and a deliberately slow `getFile()`).

**One file, one plan.** Two plans on the same file would overwrite each other's changes, so linking refuses a file another plan already uses (`findPlanForHandle()`, via `handle.isSameEntry()`), and "Open file as plan" on a file that's already a plan switches to that plan instead of adding a second one. The plan↔file association is local to each device and deliberately **not** stored inside the file: copy a file in Finder and an embedded plan id would make two files claim to be the same plan.

**Deleting** removes the plan from *this browser only* — its data, backups and file handle; the file itself is never touched, and the confirm dialog says so. The removed plan is kept in the Undo toast's closure for its 6 seconds. The last remaining plan can't be deleted (the menu item is disabled). `updatePlansIndex(fn)` is always a read-modify-write against `localStorage`, never an in-memory copy, so a second tab that added or renamed a plan isn't clobbered.

The test harness used for this drives real Chromium with `showSaveFilePicker`/`showOpenFilePicker` replaced by functions that return **OPFS** file handles (`navigator.storage.getDirectory()`): those are genuine `FileSystemFileHandle`s (they have `createWritable`, `queryPermission`, `isSameEntry` and can be stored in IndexedDB), which is the only way to exercise the sync code headlessly.

### Mandatory file linking

Every plan must be linked to a file (an explicit user request; before it, linking was optional and a plan could live only in the browser). A plan can never be *left* without a file, but it can be **disconnected and reconnected** (an explicit user request, so a wrong or moved file can be swapped for a new or different one) — see "Disconnecting" below. What enforces it:

- **`fileLinkRequired()`** = the browser supports files **and** `fileSyncStatus` is `'unlinked'` or `'missing'`. `enforceFileLink()` runs at the end of `activatePlanFile()` — i.e. on page load and after every plan switch — and opens `#fileSyncModalBg` when that holds. This one dialog covers first run, the migrated Plan 1 of an existing install (no file yet), a plan whose file link is gone, and a missing file.
- **The dialog can't be dismissed**: no × and no "Not now", the backdrop ignores clicks, and Escape leaves it alone (the Escape handler counts it as an open overlay but never closes it). Cancelling a file picker just leaves it up. It is *always* in this state — there is no closable variant, because a plan can only be unlinked while that dialog is about to open. It offers **Create new file** (the plan's current tasks are written into it) and **Open existing file** (merged into the plan, or replacing it if the plan is still empty).
- **New plan** and **Duplicate** go through `createLinkedPlan(name, data)`: the save picker opens *first*, straight from the click (needs the user gesture); only after a file is chosen is the plan created, written into the file and opened, so a plan is never in an unlinked state and cancelling creates nothing. The plan dialog's button reads "Create…" (a file dialog follows). `refuseIfFileBelongsToAnotherPlan(handle, true)` also rejects the *current* plan's file here — a new plan reusing it would overwrite it.
- **Missing file** (`fileSyncStatus === 'missing'`): `pollFileSync()` gets `NotFoundError` from `getFile()` → `markFileMissing()` stops polling, shows "File missing" on the button and re-opens the dialog (title "Linked file not found"). Only the *read* detects this: a *write* to a deleted file silently re-creates it at the same path (verified in Chromium, `createWritable()` + `close()` both succeed), so nothing is lost — the dialog is for a file that was moved or renamed.
- **Browsers without the File System Access API** (Safari, Firefox): there is no way to write a file, so requiring one would lock the app out. `fileSyncStatus` is `'unsupported'`, the file button is hidden, no dialog appears, and plans stay browser-only (New plan/Duplicate create them directly). `fileLinkRequired()` is false there.
- **Disconnecting**: the linked file button (top right) and the plan menu's "Disconnect file…" both call `disconnectFile()`, which asks for confirmation and then runs `unlinkFile()`: `flushFileSync()` first (so the file holds everything up to the last edit — an edit made just before disconnecting still lands in it), then `planEpoch++`, clear the handle/snapshot/polling, delete the `plan:<id>` handle from IndexedDB, clear `fileName` in the index — and finally `enforceFileLink()`, so the mandatory dialog opens **immediately** (an explicit user request: "force linking a file after disconnect"). The old file is never deleted or touched again. From the dialog the user can create a **new** file (the plan's tasks are written into it), open a **different** existing file (its tasks are *merged* into the plan — nothing is dropped, and the merged result is written to that file), or pick the very same file again. The "Disconnect file…" item is disabled when the plan has no file and absent in browsers without file support.
- **Tests**: with the API present the link dialog blocks the page, so older headless scripts that don't care about files disable it (`delete window.showOpenFilePicker`) and run in the browser-only fallback.

### Print / PDF

**Data → Print / PDF…**, the printer button (`#printBtn`) or **Ctrl/Cmd+P** (which replaces the browser's own print) opens `#printModalBg`: options on the left (title, paper A4 / A3 / Letter / Legal / Tabloid, orientation, the list columns ID / WBS / Task Name / Start / Finish / Days / % / Resource / Predecessors, time range whole plan or custom, timescale automatic / weeks / months / quarters, baseline, critical path, dependency arrows, today line, days off, expand every group) and a **live preview** with page navigation on the right. `buildPrintPages(options)` draws every page itself as an **SVG in a fixed coordinate system shaped like the printable area** (paper minus an 8 mm margin; 1100 units wide in landscape, 780 in portrait, the height from the paper's ratio), so the same drawing prints on any paper: title and date range, the list header (Midnight Blue `#00205B` like the Excel export) beside a two-tier timescale (weeks: months over ISO calendar weeks; months / quarters: years over months or Q1–Q4; automatic ≤ 150 days weeks, ≤ 900 months, else quarters; the timeline is **fitted to the page width**), one row per task in the order the list shows them (`visibleTaskList()`, so folded groups and filters apply; `expandAll` uses `exportTaskRows('filtered')`), group bars, milestone diamonds, progress fill, dashed Manual bars, red outlines for the critical path, the baseline as a grey line, days off and holidays shaded (weeks only), the today line, elbow arrows between tasks **on the same page**, and a footer with a legend and "Page i of n". A wide list makes the Task Name column give way so the chart keeps at least 380 units; a short plan gets taller rows (up to 22 units) so it uses the page; a long plan continues on further pages with the heading repeated (`rowsPerPage` from the height). Text is measured with a canvas and cut with an ellipsis. Colours are the light theme's (`statusColorHex`), never theme variables — a page is white whatever the app's theme. **Printing** = `mountPrintRoot(built)` adds `#printRoot` (hidden on screen; `@media print` hides everything else and shows only its `.print-page` sections, `break-after: page`) and an `@page { size: A4 landscape; margin: 8mm }` rule, then `window.print()`; `afterprint` unmounts. The browser's dialog does the printing or "Save as PDF" (no PDF library). Nothing in the plan changes. Covered by `verify_print.py` (63 checks, including a real PDF made with Playwright's `page.pdf` in print emulation: page count and A4 landscape size).

### The Help dialog

A **tabbed** dialog (an explicit user request: "improve the visuals … look at the Pulse app … if necessary make the modal multi tab"). A rail of six topics on the left — **Getting started, Scheduling, Calendar & progress, Task list, Gantt chart, Plans & data** (`HELP_TABS`, `setHelpTab(id)`, arrow keys / Home / End via `helpTabKey`; `role=tablist`/`tab`/`tabpanel`, `aria-selected`, only the selected tab is in the tab order) — and one pane per topic, each a few titled sections (`.help-section` + small uppercase `.help-section-title`) of **short icon rows** (`.help-row`: a Font Awesome icon, then text with the key term in bold; `<code>` for syntax such as `3FS+2`, `<kbd>` for keys, `.help-tip` for a note), separated by `.help-divider`, like Pulse's help. The dialog has a fixed height (`min(690px, 88vh)`) so switching topics never resizes it; a long pane scrolls inside itself; under 660px the rail becomes a strip along the top. `openHelpModal(tab?)` reopens on the topic last read (`helpTab`, per session, not stored). Colours come from the theme tokens; the tab labels use `--text` and the section titles `--text-dim` (contrast ≥ 4.5:1 in both themes — accent-coloured text failed on the dark panel, so the active tab is marked by a bar and the icon instead). **Keep the Help in step with the app**: when you add or change a feature, edit the row in the matching topic (write one short row, not a paragraph). Earlier the whole Help was one modal body of long paragraphs, and a leftover fragment of an old paragraph once closed that body early so most sections spilled out of the scrolling area — `verify_help.py` (24 checks: structure, switching, constant size, keyboard, remembered topic, closing, content per topic, icons, row length, contrast in both themes, narrow layout) and the well-formedness check in `verify_e2e.py` guard against it.

### PWA

`manifest.json` + `sw.js` (cache-first app shell with network-first navigation, same shape as Pulse's own service worker) + `icons/` (`icon.svg` source plus `icon-180/192/512.png`). **The logo is a solid diamond (the standard Gantt milestone symbol) with three staggered Gantt bars cut out of it — deliberately not on a circle, an explicit user request, and chosen over four other candidates for staying legible at the top bar's 26px.** It appears in three places that must change together: the top-bar `.brand` SVG, the About dialog SVG (both inline, `fill="currentColor"` so they follow the theme, each with its **own unique `<mask id>`** — two inline SVGs sharing a mask id makes the second one render blank/wrong), and `icons/icon.svg`. The icon is a *full-bleed* accent (`#0969da`) square with the white mark at 70% scale — no rounded corners, since iOS and Android apply their own mask and a pre-rounded tile would show a dark/white corner; the mark sits inside the maskable safe zone. The PNGs are rendered from `icon.svg` with headless Chromium (screenshot an `<svg>` sized to each target; no SVG rasterizer is installed), e.g. via Playwright `page.set_content(svg)` + `page.screenshot(clip=...)`. Bump `CACHE_NAME` in `sw.js` when the icon changes so installed copies refresh it. `start-milestone.command`/`stop-milestone.command` mirror Pulse's own local-server launch scripts, on port 8937 (Pulse's own is 8936 — kept distinct so both apps' dev servers can run at once).

## Known v1 limitations

- The critical path ignores constraints other than the current dates and still includes completed tasks (see "Scheduling engine").
- No working hours or per-task calendars; holidays come from a preset list of about 30 regions or are entered by hand (see "Working calendar (per plan)"); lags are working days only.
- Auto scheduling is bidirectional like MS Project (see "Auto scheduling is bidirectional"); what MS Project does that this doesn't: reschedule the *remaining* work of a started task from a status date, resource levelling, and "tasks will always honor their constraint dates" as a switchable option (constraints always win here). Baselines are manual and there are eleven of them (see "Baselines, actual dates and variance"); actual dates overwrite Start/Finish, so an early actual finish pulls its Auto successors earlier.
- ALAP behaves identically to ASAP — no backward slack-filling pass yet (see "Task constraints" above).
- SNLT/FNLT (Start/Finish No Later Than) are flagged when violated, never enforced — placement is by the earliest date the links and lower bounds allow, with no backward pass.
- Two browser tabs on the *same* plan still race each other in `localStorage` (last write wins); with a linked file the write-time merge protects the FILE, not the other tab's memory. Two tabs on *different* plans are fine.
- No RBAC/roles, no daily-backup-to-a-linked-folder, no multi-file sync split — all deliberately out of scope for a single-user, single-project local planner (unlike Pulse, which is a multi-role team dashboard).
