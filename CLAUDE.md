# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Overview

Milestone is a single-file, zero-dependency HTML application — the entire app (HTML, CSS, JavaScript) lives in `milestone.html`. There is no build step and no package manager. It's a local-first project planner: a single Gantt chart with a work-breakdown hierarchy (parent/summary tasks roll up dates and progress from their children), predecessor/successor dependencies (Finish-to-Start/Start-to-Start/Finish-to-Finish/Start-to-Finish with lag), auto-scheduling (moving a task forward cascades to its dependents), and a critical-path view. The app holds several independent **plans** (each with its own tasks, backups and its own linked file — linking is mandatory, see "Mandatory file linking") behind a switcher in the top bar — see "Plans" below. It's also an installable PWA (manifest, service worker, icons), and shares the same data-durability feature set as this author's other single-file apps (Pulse, mytasks): JSON export/import, rolling local backups, deletion tombstones with undo, and File System Access API file sync (mandatory here, unlike in the other apps).

**Sibling projects**: [Pulse](../Pulse/CLAUDE.md) (a programme dashboard) and mytasks (a task manager) are this same author's other single-file apps — Milestone's PWA setup and data-durability mechanisms are ported from Pulse (see its own CLAUDE.md for the fuller narrative history behind those patterns; Milestone's own version below is the same design, freshly built rather than copy-pasted). Milestone also initially ported Pulse's switchable color-scheme system but later dropped it for a single fixed palette — see "Fixed color palette" below.

**Naming**: the app was originally called dbPlanner and renamed to Milestone — everywhere, including the source file (`milestone.html`), launcher scripts (`start-`/`stop-milestone.command`), repo and directory. The one deliberate holdover is the migration code: the persistence keys were renamed `dbplanner-v1`/`dbplanner-backups` → `milestone-v1`/`milestone-backups` and the IndexedDB database `dbplanner-fs` → `milestone-fs`, and `migrateLegacyStorage()` / `_fsMigrateLegacy()` in the script copy anything found under the old names forward on first load (copy, not move — the old entries are left as a rollback copy, and the new keys always win so a later edit is never clobbered by the stale legacy copy). Keep that code for as long as an install predating the rename might still exist; it's the only place the old names should still appear. (`milestone-v1`/`milestone-backups`/the IndexedDB `syncFile` key are also the source of the *plans* migration — see "Plans".)

## Running it

A plain `file://` open of `milestone.html` works for quick checks, but PWA install/offline support requires serving it over http — browsers refuse to register a service worker for `file://` pages. `./start-milestone.command` serves the directory on `http://127.0.0.1:8937` and opens it in Chrome/Edge (Safari can't install this kind of PWA on macOS, and the File System Access API sync feature is Chrome/Edge-only regardless of how the page is served). `./stop-milestone.command` kills the server.

There is no automated test suite yet (unlike Pulse/mytasks' JXA-based one) — verified so far by driving the app end-to-end in a real headless Chromium via Playwright (add/edit/delete tasks, dependency cascade, drag-to-reschedule cascade, critical path) with a clean console. Add a real test harness if this app's surface grows enough to need one.

## Architecture

The file has three logical sections in order: CSS styles, HTML structure, and a `<script>` block containing all application logic — same convention as Pulse/mytasks.

### Data model

State lives in `localStorage`, split into the **plans** and the **device preferences**:

| key | holds |
|---|---|
| `milestone-plans` | `{ current, plans: [{ id, name, fileName }] }` — the index; `name`/`fileName` are cached copies so the switcher can list plans without loading them |
| `milestone-plan-<id>` | one plan: `{ version: 1, project: { name, updatedAt, newTaskMode: 'auto' \| 'manual', modeRev: 1, fieldNames: { text1: 'Cost centre' } }, tasks: [Task], deletedTaskIds: [{id, deletedAt}] }` — exactly `syncPayload()`, i.e. exactly what is exported, backed up and written to that plan's linked file |
| `milestone-backups-<id>` | that plan's daily snapshots |
| `milestone-prefs` | `{ theme, zoom: 'week' \| 'month' \| 'year', zoomRev, view, gridPaneWidth }` — per-device display preferences, shared by every plan |

The prefs are deliberately kept out of `syncPayload()` and out of the plan data, matching Pulse's "personal preference stays local" convention (and so switching plans never flips your theme or zoom). IndexedDB `milestone-fs` holds one `FileSystemFileHandle` per plan under the key `'plan:' + id`.

A **task**:
```js
{
  id, name, parentId: null|id, order: Number,
  startDate: 'YYYY-MM-DD', endDate: 'YYYY-MM-DD',   // equal when milestone is true
  progress: 0-100,
  milestone: Boolean,
  color: null | 'blue'|'teal'|'purple'|'amber'|'pink'|'green'|'red'|'grey',  // null = auto (by status)
  predecessors: [{ id: taskId, type: 'FS'|'SS'|'FF'|'SF', lag: Number }],  // days, can be negative
  collapsed: Boolean,   // hierarchy expand/collapse state
  taskMode: 'manual' | 'auto',            // MS Project Task Mode — see "Task Mode" below
  startText/endText/durText: null | String, // free-text Start/Finish/Duration, manual tasks only
  // (There is no `notes` field any more — removed at the user's request. Text an older version stored under `notes` is left
  //  untouched in the data, so nothing is lost, but it is no longer shown, edited or exported, and new tasks don't get the key.)
  custom: { text1: 'x', number2: 4.5, date3: 'YYYY-MM-DD', flag4: true },   // custom fields (below); only fields that have a value are present, the object is absent when empty
  resource: String,                        // who does the work, free text ("Anna, Ben"), '' = none
  actualStart: null | 'YYYY-MM-DD',        // what really happened — kept apart from the plan; a task's SUCCESSORS are scheduled off them (see "Actual dates drive the schedule")
  actualFinish: null | 'YYYY-MM-DD',       // (WBS, Remaining Duration and Status are *computed*, never stored — see "Task fields and columns")
  updatedAt: Number      // Date.now() — last-write-wins timestamp for merge
}
```

**A task with children is a summary/rollup task**: its effective start/end/progress are computed at render time from its descendants (`effectiveDates()`, memoized per render pass) rather than stored — for an Auto summary, dragging or editing its own bar isn't supported, only its leaf descendants (a *Manually Scheduled* summary is the exception: it owns its dates — see "Task Mode"). `normalizeData()` enforces this both ways: a task that has children has its own `predecessors` forcibly cleared (a summary task can't itself be independently scheduled), and no task can pick a summary task as its predecessor (the predecessor picker in the task modal only lists leaf tasks).

### Scheduling engine

`constraintStart(task)` computes a task's earliest allowed start from its own `predecessors`, per dependency type (FS/SS/FF/SF, each with its own lag). `cascadeSchedule(changedId)` walks forward through the successor graph from `changedId`, pushing a dependent task's dates later whenever its constraint is violated, and continuing on to *its* successors — implemented as a plain worklist/relaxation loop (not a single topological pass), since a diamond-shaped dependency graph can need a downstream task revisited after a second predecessor's own cascade lands. It only ever pushes a task **later**, never pulls one earlier — a task placed manually ahead of its own constraint is left alone (surfaced as a visual warning via the cycle-detection icon's sibling styling, not silently corrected), so a deliberate early placement is never overwritten by an unrelated edit elsewhere in the chain.

**Leads and lags** are the same `lag` field, just signed: a positive value is a lag (delays the dependent task, e.g. "wait 2 extra days after the predecessor finishes"), a negative value is a lead (lets it start early and overlap its predecessor, e.g. "start 2 days before the predecessor finishes"). The engine never distinguished the two — `addDays(pred.endDate, 1 + lag)` and friends in `constraintStart()` already handled negative `lag` correctly from the start — but nothing in the UI ever said so, so it read as a lag-only field. The modal's lag input, the inline grid Predecessors field's placeholder, and the in-app Help panel's Dependencies section now all spell out that negative values create a lead, rather than requiring a user to already know MS Project's terminology to discover it works.

`taskCycleSet()` (plain DFS over the predecessor graph, recursion-stack based) finds every task participating in a circular dependency; those tasks are excluded from `cascadeSchedule()`'s traversal entirely and flagged with a warning icon in the grid rather than crashing or looping.

**Task Mode** (`task.taskMode`: `'manual'` | `'auto'`) copies MS Project's Manually Scheduled vs Auto Scheduled. Where the two behave differently:

- **Cascade**: a `'manual'` task is skipped by `cascadeSchedule()` and by `applyConstraints()`'s self-shift, so predecessors never move it — but it still keeps its dates for *its own* successors' `constraintStart()` to read. Its own constraint is ignored too (`constraintViolated()` returns false, the MSO/MFO pin in `saveTaskFromModal()` is skipped).
- **Default**: new tasks are **Auto Scheduled** (`project.newTaskMode`, changed with the "New tasks:" button at the right of the sub-bar; it lives on `project`, so it syncs). It started as Manual, like MS Project, and was changed at the user's request. Because `normalizeData()` had written `'manual'` into every project on its first save, a project without the revision marker `project.modeRev === 1` is switched to Auto **once** on load (and gets the marker) — a choice made afterwards keeps the marker and is never overridden; existing tasks keep their own modes, only the default for *new* tasks moves. Tasks with no stored `taskMode` — anything saved before Task Mode existed — normalize to Auto so old projects keep behaving as they did.
- **Switching to Auto** (`setTaskMode()` / the dialog → `rescheduleAsAuto()`): drops free-text dates and moves the task to `constraintStart()` — the earliest date its links/constraint allow, **earlier or later** than where it sat. This is the only place a task is ever pulled earlier; the ongoing cascade is still push-later-only (see above). With no links there's nothing to schedule against, so dates are kept.
- **Free-text dates**: a manual task's `startText`/`endText`/`durText` (`null` = a real value; `''` = blank; otherwise arbitrary text like "TBD"). `startDate`/`endDate` always stay valid ISO placeholders so the rest of the code never sees a non-date. `isUnscheduled(t)` (manual with a text Start *or* Finish) means: no Gantt bar, ignored as a predecessor by `constraintStart()`, excluded from summary rollups (`effectiveDates()` returns `start: null`) and from `computeDateRange()`. With exactly one known date the Gantt draws a bracket (`.gantt-bracket`) at it. `normalizeData()` nulls all three for Auto tasks and milestones' Finish/Duration. The task dialog leaves the text alone unless the corresponding date field was actually changed (`modalOrigDates`).
- **Schedule warning**: `scheduleMismatch(t)` — a manual task whose links (`constraintStart(t, false)`, constraints excluded) say it can't start before a date later than its own start. Shown as a warning triangle in the grid and an amber outline on the bar. It only flags "starts too early"; a manual task placed *later* than its links need is not warned about.
- **Manual summary tasks**: a summary with `taskMode: 'manual'` keeps its *own* stored dates instead of rolling up (`effectiveDates()` also returns `rollStart`/`rollEnd`, drawn as a thin `.gantt-rollup` bar under it), and its Start/Finish/Duration are editable. Progress still rolls up. Note the consequence of Manual being the default: indenting a task under a Manual parent does **not** make the parent span its children until it's set to Auto.
- **Critical path** excludes manual tasks (`computeCriticalPath()`) — MS Project doesn't compute criticality for them either.

UI: its own grid column before Task Name (`.task-mode-cell`, pushpin/amber = manual, chart icon/dim = auto — the constraint indicator is a calendar icon now, so the pushpin means only one thing). Clicking it opens one shared popup (`#taskModeMenu`, `openTaskModeMenu(event, target)`; `target` is a task id or `'new'` for the sub-bar button) listing the two named modes with a check on the current one; the task dialog has a matching Task Mode select. Manual bars are dashed with a paler fill, manual milestones are hollow diamonds. A manual task's inline Start/Finish editor is a text box (`inlineTextDateHtml()`, accepts `DD.MM.YYYY` or ISO via `parseUserDate()`, anything else is kept as text) with a calendar button that borrows a hidden native `<input type="date">` for its picker; `inlineBlur()` treats focus moving between the two as still editing. With the native popup open, the first Escape closes the popup and a second cancels the edit.

**`applyConstraints(taskId)` vs `cascadeSchedule(taskId)`** — two different call sites need two different things, and using the wrong one silently drops the dependency: `cascadeSchedule()` alone only pushes `taskId`'s *successors*, assuming `taskId`'s own dates just changed by an intentional, already-valid action (a drag). Saving the task modal or drag-linking a new dependency changes `taskId`'s own *predecessor list*, not its dates — `taskId` itself may now violate a constraint nothing has re-checked yet. `applyConstraints()` checks `taskId`'s own constraint first (shifting it if needed) and *then* cascades to successors; `saveTaskFromModal()` and the drag-to-link handler both call `applyConstraints()` for this reason, while the bar-drag handlers call `cascadeSchedule()` directly.

**Critical path** (`computeCriticalPath()`) is a standard forward/backward CPM pass (earliest start/finish, then latest start/finish from the project end, slack = latest − earliest, critical when slack ≤ 0) over leaf tasks only. **Known v1 simplification**: every dependency is treated as Finish-to-Start for this specific slack calculation, regardless of its real type — SS/FF/SF links still drive the actual forward-scheduling cascade above correctly, just not this slack math. Good enough for highlighting the dominant chain; a mixed-type project's critical path may be approximate.

### Task IDs are collapse-stable, and drive predecessor/successor selection

`taskDisplayId(id)` is a task's 1-based position in the *full* outline order (every task, ignoring `collapsed`) — deliberately not `visibleTaskList()`'s own collapse-aware order, which is what row rendering uses. This is what makes an ID usable as a stable reference at all: collapsing a parent elsewhere must never renumber a still-visible task's own ID, or a predecessor link recorded by id (the data itself is always stored by internal `task.id`, never by this display number) would read as pointing to a different row than the one a user actually picked. `resetIdCache()`/`_idIndexCache` follow the identical per-render-pass caching shape `resetEffectiveCache()`/`_effCache` already established.

Every place a task is chosen or shown as a predecessor/successor leads with this ID, not its name: the grid's own Predecessors column reads as a compact `3FS+2`-style reference (id + dependency type + signed lag) rather than a truncated task name — both shorter and immune to a later rename, matching how real MS Project's own Predecessors column reads. The task modal shows the task's own ID and WBS code as a badge next to its title (`#taskModalIdBadge`, e.g. `#4 · WBS 2.1`). There used to be a read-only **Successors** list under Predecessors in the dialog; it was **removed at the user's request** (`renderSuccessorsList()` and its CSS are gone). `successorsMap()` stays — `cascadeSchedule()` needs the reverse index.

**The predecessor picker is a plain numeric field, not a dropdown — an explicit user request, and also just how real MS Project's own Predecessors column works: type the task's number directly.** `onPredecessorIdChange(i, value)` resolves the typed number via `taskIdByDisplayId()` (the reverse of `taskDisplayId()`) on blur/Enter, not on every keystroke — a self-reference, a nonexistent ID, a summary task, or a duplicate already in the list all get rejected with a toast and the field clears back to empty rather than silently accepting something wrong; a freshly-added row starts genuinely empty (`{id: null, ...}`) rather than defaulting to an arbitrary task the way a `<select>`'s own first option would. `saveTaskFromModal()`'s existing `editingPredecessors.filter(p => p.id)` is what quietly drops a row that's still empty or still invalid at Save time, with no separate validation step needed. The field's native up/down spinner is hidden via `.pred-id-input` CSS (`-webkit-appearance:none` on the spin buttons, `-moz-appearance:textfield` on the input) — it was resolving/replacing a typed ID rather than doing anything useful, since a Task ID isn't a value you'd ever want to increment.

### Inline grid editing (Task view only)

`editingCell` (`{id, field}` or `null`) tracks which single cell, if any, is mid-edit — pure transient UI state, not persisted, reset by `setView()` and `openTaskModal()` so a stray edit never survives a view switch or the modal taking over. `renderGrid()` swaps that one cell's static `<div>` for an `<input>` (via each cell's local `editing('field')` check) rather than reworking the whole row into a form; every other cell keeps rendering normally. Clicking a static cell calls `startInlineEdit(id, field)`, which re-renders and then focuses/selects the new input on the next frame (the input doesn't exist yet at click time). Enter blurs the input (triggering commit); Escape calls `cancelInlineEdit()` directly, clearing `editingCell` before the resulting re-render can remove the focused input out from under a pending blur — `commitInlineEdit()` guards on `editingCell` still matching `{id, field}` so that stale blur is a no-op instead of double-committing or committing after cancel.

Only leaf tasks get start/finish/duration/predecessors inline editing — except a *manually scheduled* summary, which owns its own dates and so gets start/finish/duration too (an Auto summary's dates are computed rollups — see `effectiveDates()` above — so there's nowhere to write); milestones additionally skip finish/duration (forced equal to start by definition). Auto tasks get the native date input; Manual tasks get the free-text editor described under Task Mode. `commitInlineEdit()` stamps `updatedAt` (inline edits previously didn't, which would have let a stale copy win a last-write-wins merge). All of this mirrors the task modal's own rules, just enforced at the point where the click would start an edit rather than after the fact.

Typing into the inline Predecessors cell reuses the same compact `3FS+2` syntax the grid displays (`parsePredecessorString()`), but unlike the modal's per-row picker this one field represents the task's *entire* predecessor list at once — so a single bad token (typo, self-reference, summary task, unknown ID) rejects the **whole** edit and leaves the existing list untouched (returns `null`, `commitInlineEdit()` skips the assignment) rather than silently keeping only the valid tokens and dropping the rest. Losing an already-correct predecessor to an unrelated typo elsewhere in the same string would be a much worse failure mode than just rejecting the edit outright.

Empty grid cells (no predecessors yet, blank duration) used to collapse to zero height under `align-items: center`'s default content-sizing, making an empty Predecessors cell unclickable — `.grid-cell-dim` now sets `min-height: 1em; align-self: stretch; display: flex; align-items: center` so a cell with no text still occupies its full row height.

**Date editors outgrow their column while open.** Start, Finish, Actual Start, Actual Finish and custom Date cells all edit with either the native `<input type="date">` (Auto tasks) or the typed box + calendar button (`.inline-wrap`, Manual tasks). The native control needs ~127px to show `dd.mm.yyyy` *and its picker icon*, but the Actual columns are 92px (and Start/Finish 116px), so a plain `width: 100%` clipped the icon — the picker was unreachable. Now `input.inline-edit[type=date]` and `.grid-row > .inline-wrap` get `width: max(100%, 132px)`, `z-index: 4` and (wrapper) `overflow: visible`: the open editor grows to the right over its neighbour cell; the closed cell keeps its narrow width. Any new date editor placed as a direct child of `.grid-row` inherits this; don't shrink these below ~127px. Covered by `verify_date_editors.py`.

### Column lines (Tasks view)

A fine vertical line in `var(--border)` — the colour of the divider between list and chart in the Gantt view — separates the columns of the Tasks-view grid, in the header and in every row, and runs on down the empty area under the last task. **They are not cell borders**: the tracks mix `px` and `fr`, the cells have 6px gaps, and the date editors overflow their cell (see above), so borders would fight all of that. Instead `updateColumnLines()` (called from `render()`, and by a `ResizeObserver` on `#gridPane`, falling back to `window.resize`) reads the *resolved* `grid-template-columns` of `#gridHeader` and of the first row, puts a line in the middle of each gap (none before the row-actions column at the far right) and publishes them as CSS variables on `#main`: `--col-lines-h`/`--col-pos-h` (header) and `--col-lines-r`/`--col-pos-r` (rows; the header and rows are measured separately because a scrollbar can narrow the rows only). `.grid-header::before` / `.grid-row::before` (absolute, `pointer-events: none`) paint the header/row variables as 1px gradient layers, `.grid-rows` paints the row variable for the empty area below (rows are transparent, so they coincide; a hovered/selected row's own background can't hide its lines because they live on the pseudo-element). The Gantt view's side list has no column lines; with no rows the header keeps its lines and the body has none. Covered by `verify_column_lines.py`.

### Where Add Task puts the new task

`addTask()` inserts the new task **directly below the selected one** (an explicit user request): right after a leaf task as its sibling, or as the *first sub-task* of a summary task (expanding it if it was collapsed so the new row isn't hidden); with nothing selected it's appended to the end of the top level. The new task becomes the selection, which is what makes repeated Add Task stack downward — without that, every add would land directly under the *same* selected row and the run would come out reversed. The level's siblings are then renumbered `0..n` with the new task in its slot; only siblings whose `order` actually moved get a fresh `updatedAt`, since `order` is a merged field and an un-stamped renumber would never reach another device (the same rule `reorderItem()` follows in Pulse).

### Clone task (`cloneTask(id)`)

A **Clone** button on every task row (Tasks view; it appears on hover between Edit and Delete — the row-actions column is 82px for the three buttons) and one in the sub-bar (`#cloneTaskBtn`, acts on the selected task, disabled without a selection). It copies the task **and everything below it, at every depth**:

- **Exact copy**: each task is a `JSON` deep copy (dates, %, actual dates, mode, constraint, colour, resource, milestone flag, custom fields, free-text dates …) with a **fresh id**; sub-tasks get their cloned parent's id. Only the top task's name gets ` (copy)`; the sub-tasks keep theirs. `updatedAt` = now, so a sync sees new tasks.
- **Placement**: directly under the original at the same level (its sibling, `order + 1`); that level is renumbered, and only siblings whose order really moved get a fresh `updatedAt`. The clone is selected, added to `filterPinned` (an active filter can't hide it), and keeps `collapsed` as the original had it. The dialog is *not* opened.
- **Dependencies**: a link **between cloned tasks** is re-pointed at the clones (type and lag kept, at any depth); a link to a task **outside** the clone is kept, so the copy is scheduled exactly like the original; nothing outside the clone starts depending on it. (Summary tasks can't have predecessors — `normalizeData()` strips them — so only leaf tasks carry links.) No cascade runs: the clone sits on the same dates.
- **Undo** (toast): removes every clone, tombstones their ids (`deletedTaskIds`, so a sync can't resurrect them), restores the moved siblings' order and the previous selection.

### Task fields and columns

Besides name, dates, duration, %, predecessors and a colour, a task has **stored** fields `resource` (free text, ≤200 chars), `actualStart` and `actualFinish` (real dates or null; sanitised by `normalizeData()` via `parseUserDate`), and **computed** ones that are never stored:

- **WBS** — `wbsCode(id)`: the outline position as `1`, `1.1`, `1.2.3` (like MS Project's default WBS), cached per render in `_wbsCache` (cleared by `resetIdCache()`; the Excel export calls it too). Like the ID it ignores collapsing and filtering, and it renumbers itself on reorder/indent. Read-only — there is no custom-WBS override.
- **Actual Start / Actual Finish** — `actualDates(id)`: a task's own; a group **rolls up** — the earliest actual start of anything below it, and an actual finish only once *everything* below has one (then the latest). A group's cells and dialog fields are read-only (the dialog says why) and saving a group never writes its rolled-up dates into itself. An Actual Finish before the Actual Start is refused (toast) in both the inline editor and the dialog; the dialog checks *before* changing anything. **A milestone happens on one date, planned and actual**: like `endDate = startDate`, `normalizeData()` forces `actualFinish = actualStart`; the dialog hides **Actual Finish** together with Finish and Duration (`#taskActualFinishField`, toggled in `onMilestoneToggle()`), the list's Actual Finish cell isn't editable for a milestone, and editing its Actual Start moves both — so a milestone with an actual date is `Complete` (it has happened) with no extra rule in `statusOf()`. (Actual Finish used to stay visible on milestones while Finish was hidden, which read as "Finish is missing".) **They do not couple to % complete** (MS Project sets 100% on an actual finish; not done here). **A task's own planned dates are never rewritten by its own actuals — but its successors are scheduled off them:** see the next section.
- **Remaining Duration** — `remainingDays(id)`: `duration × (1 − % complete)` in days, one decimal (`2.5 days`); blank for milestones and free-text durations.
- **Status** — `taskStatus(id)`, judged against *today*: `Complete` (100 %, or an actual finish), `Late` (not complete and past its finish, or should have started and hasn't), `Future Task` (not started, start ahead), `On Schedule` (everything else); blank when there is nothing to judge. "Started" = some progress *or* an actual start. Shown as a coloured pill (`.status-pill`).

**The task dialog shows every field.** Stored ones are inputs (Resource sits beside Task Mode; Actual Start/Finish under Duration/%). The three *computed* ones — **WBS, Remaining Duration, Status** — appear in a dashed read-only row (`.calc-row`, `.ro-value`) under the actual dates, so nothing that is a column in the list is missing from the dialog. `updateModalComputed()` refreshes that row from what is **currently typed** (it uses the pure helpers `remainingOf()` and `statusOf()` that the list columns also use, via `remainingDays()`/`taskStatus()`), so it follows edits live; it is wired as an `input`/`change` listener on `#taskModalBg`, which runs after each field's own `onchange` has synced the dates and duration. A group shows its rolled-up values, and a task whose dates are still free text ("TBD") shows "—" until it is given real dates (`modalOrigDates` tells untouched from edited). Nothing here is stored. The dialog is `.modal.roomy` (540px wide, up to 94vh) because it holds a lot of fields; on a normal-height window it needs no scrolling.

**Custom fields** (an explicit user request): **Text1–5, Number1–5, Date1–5, Flag1–5** — 20 fields per task, hidden by default, enabled in the column picker, shown in their own tab of the task dialog, renamable, with the names **kept per plan**.

- **Storage.** A task's values are `task.custom` (`{ text1: 'x', number2: 4.5, date3: '2026-09-01', flag4: true }` — a flag is stored only when set, and nothing empty is stored; the object disappears when it would be empty). The *names* are `project.fieldNames` (only the ones that differ from the default `Text1`…), which is why they belong to the plan: they are part of `syncPayload()`, so they are exported, backed up, written to the plan's file and merged (last write wins on `project.updatedAt`, which renaming stamps), and two plans can call the same field different things. `cleanCustomValues()` and the block at the end of `normalizeData()` sanitise both on every load/merge/import: unknown keys dropped, text trimmed and capped at 255, numbers must be finite (`12,5` is accepted), dates must be real, names trimmed, capped at 40, and a name equal to the default is dropped.
- **Registry.** `CUSTOM_KINDS` / `CUSTOM_FIELDS` define the 20; each is also an entry in `TASK_COLS` (`custom: true`, `dflt: false`) and `FILTER_COLS` (text → text rules, number → number rules, date → date rules, **flag → a Yes / No list**, Yes first), whose `label` is a **getter** (`customFieldName(id)`), because it depends on the current plan. Because they are ordinary columns, the Columns menu, ordering, persistence and the "new columns arrive hidden" rule in `loadPrefs()` needed no special handling. **Field names are user text, so every place that puts a label into HTML escapes it** (header, menu, aria-labels, filter panel and chips, dialog tab).
- **The list.** `customCellHtml()`: Text/Number/Date click to an inline editor; a **Flag toggles on click** (`toggleCustomFlag`, a green tick). The inline **number editor is a text box** (`inputmode="decimal"`), not `type=number` — a native number box refuses to let you type the invalid part, so "12,5" or a typo could never be handled; it is parsed on commit (`isn't a number` toast, nothing changes). Any task can have custom values — groups and milestones included — and nothing is rolled up.
- **The dialog.** Two tabs, **General** and **Custom fields** (`.modal-tabs`, `setTaskModalTab()`); the dialog always opens on General and the Custom tab carries a badge with the number of values set (`updateCustomBadge()`, live). The tab is four sections (`renderCustomFieldsTab()`), inputs `cf_<id>`, read back by `readCustomInputs()`; Save writes both tabs. A validation error raised on the General tab (Actual Finish before Actual Start) switches back to General so it is visible.
- **Renaming.** A pencil beside each custom field — in the Columns menu and on the Custom tab — opens `#fieldNameModalBg` (`openFieldNameModal`/`saveFieldName`). A name must be unique among the custom fields *and* the standard columns (case-insensitive), 1–40 characters; an empty name, the default name, or **Use default name** removes the override. Renaming from the dialog re-renders the tab **with what is currently typed**, so unsaved input survives. The rename dialog sits after the task dialog in the page so it opens on top, and **Escape closes only the topmost one** (the general handler closes every open modal, which would have thrown away the task dialog's edits).
- **Excel.** "As shown" exports the enabled custom columns, headed with the plan's names (Date as a real date, Number as a number, Flag as Yes/No); "All columns" adds only the custom fields **in use** (renamed or holding a value), not twenty empty columns.
- **The Columns menu** now has 33 rows: it scrolls (`max-height` is set when it opens), keeps its scroll position across the re-render every tick/move triggers, and shows a rename pencil on custom rows.

**Default column sequence** (an explicit user request — the order the user arranged and asked to make the default): Mode, WBS, Name, Start, Finish, Actual Start, Actual Finish, Duration, %, **Predecessors, Remaining Duration, Status**, Resource, then the 20 custom fields. It is the insertion order of `TASK_COLS`; "Reset to default" restores it. Installs keep whatever order they have saved.

**Two-line column headers** (Tasks view only): a header may run to two lines. `colHeadHtml()` turns a `\n` in a label into `<br>` — used for `Task/Mode`, `Actual/Start`, `Actual/Finish`, `Remaining/Duration` — and any other header (a long custom name) wraps naturally, clamped to two lines with an ellipsis (`-webkit-line-clamp`). This is what lets Task Mode be 64px and the actual dates 92px wide. The header row is 42px there (task rows stay 32px); the Gantt view's side list keeps its one-line 32px header because it has to line up with the chart's timescale.

**The Predecessors column is only as wide as its header** (an explicit user request): a fixed `122px` — measured need is about 116px (header text 95px + funnel 18px + gap 3px on macOS), plus a little slack for other fonts — where it used to be `1fr` and took a large share of the spare width; Task Name (`minmax(160px,1fr)`) is now the one column that flexes. It must be a *fixed* width, not `max-content`: every row is its own grid, so a content-sized track would differ from row to row and the columns would no longer line up. A long reference list (`1FS+2, 2SS-1, 3FF+12`) is therefore cut with an ellipsis in the cell; the tooltip and the editor show all of it.

**Dialogs that fade in can't be focused on the next animation frame** — the element is still invisible then, so `focus()` silently does nothing. `openPlanModal` and the field-rename dialog used `requestAnimationFrame` and never put the cursor in their name field; they use a 40 ms timer now, like the task dialog does.

### Actual dates drive the schedule (successors), and they are edited like the other dates

An explicit user request: Actual Start / Actual Finish are date fields like Start / Finish, and **a task whose predecessor has actual dates is scheduled from them**. `constraintStart()` reads each predecessor through `linkStart(pred)` / `linkEnd(pred)` instead of `pred.startDate` / `pred.endDate`:

- `linkStart` = `actualStart` if recorded, else the planned start — used by **SS** and **SF** links.
- `linkEnd` = `actualFinish` if recorded; else, **if the task has started, its projected finish** = `actualStart + (planned duration − 1)` (MS Project-style: a task that began late finishes late); else the planned finish — used by **FS** and **FF** links. Only the *projection* is used for successors — the task's own Start/Finish stay the plan, so the Finish column can differ from what its successors are scheduled from after a late start.
- Everything else about the link is unchanged: lag/lead, the latest of several predecessors wins, milestones (their actual finish *is* their actual start), summary tasks can't be predecessors.

**It follows the engine's one-way rule.** The cascade still only ever pushes a task *later*: a late actual start / finish pushes Auto successors later, but a predecessor that started or finished *earlier* than planned does **not** pull its Auto successors forward, and clearing an actual date afterwards doesn't pull them back. (An early start does shorten the projection, so *Reschedule as Auto* / switching a task to Auto — the only place a task moves earlier, via `constraintStart()` — picks it up.) Manual tasks are never moved by the cascade, but `scheduleMismatch()` (which uses `constraintStart(t, false)`) warns from the actual dates too.

**Recording an Actual Finish completes the task** (`recordActualFinish(t, previousFinish)`, as MS Project does): `progress = 100`, and an empty Actual Start is filled with the planned start (or the finish itself if that would be later). It only fires when the Actual Finish is *new or changed* — editing % complete afterwards, or re-saving the dialog with the same finish, leaves everything alone; summary tasks are excluded (their actual dates are rollups); milestones (actual finish = actual start) complete the same way. It runs from the inline edit (toast "Actual Finish recorded — marked 100% complete") and from `saveTaskFromModal()`; in the dialog `onActualFinishChange()` / `onActualStartChange()` show the effect live in the % complete / Actual Start inputs. Clearing an Actual Finish does **not** reset % complete.

**Triggers:** recording or editing an actual date in the list calls `cascadeSchedule(id)`; saving the task dialog already ends in `applyConstraints()`, which cascades. `normalizeData()` and merges don't cascade (as for planned dates). The critical path (`computeCriticalPath()`, durations only) and the Gantt bars (planned positions) are unchanged.

**Editors** — "handled like the normal date fields": an actual date (and a custom *Date* field) uses the very same in-list editor as Start/Finish: `dateEditor()` gives an **auto** task the native date input and a **manual** task the typed box + calendar button (`inlineTextDateHtml`, placeholder `dd.mm.yyyy`), which accepts `18.09.2026` or `2026-09-18`. The one difference is deliberate: **Start/Finish of a manual task may be free text ("TBD"), an actual date may not** — it has really happened — so anything that isn't a date is refused with a toast. An Actual Finish before the Actual Start is refused as before.

**The column system.** `TASK_COLS` is the registry for the **Tasks view's** list (the Gantt view's side list stays a fixed ID/Mode/Name/Start/Finish): `label`, CSS grid `width`, `dflt` (shown until the user says otherwise) and `locked` (Task Name can't be hidden). Its insertion order is `DEFAULT_COL_ORDER`. **Task Mode's header**: the column used to be a bare 24px icon column with only a funnel in its header (its name just a tooltip); in the Tasks view it is now 98px wide with a real "Task Mode" header (the icon sits left-aligned under the label), while the Gantt side list keeps the 24px icon column, where there is no room for a label (`colHeadHtml(full ? 'Task Mode' : '', 'mode')`). **Shown by default: Mode, WBS, Name, Start, Finish, Duration, %, Predecessors; hidden: Actual Start, Actual Finish, Remaining Duration, Status, Resource.** (WBS was hidden at first and made a default at the user's request — see `COLS_REV` below.) The ID column is always first and the row actions always last. `renderGrid()` builds each row's cells into an object keyed by column id and joins them in `visibleTaskCols()` order, and sets the grid template as the CSS variable `--task-cols` on `#main` (`.main.view-tasks .grid-header, .grid-row` read it) — so a header, its filter button and its cells can never disagree.

The **Columns** button (toolbar, Tasks view only) opens `#columnsMenu`: a tick per column, ▲▼ arrows that move a column within the full list (hidden ones included, so the list you see *is* the order), a locked Task Name, and "Reset to default". `toggleColumn`/`moveColumn`/`resetColumns` update `colOrder`/`colHidden`, `save()` and re-render both the list and the menu. The choice is a **per-device preference** stored in `milestone-prefs` as `cols: { order, hidden }` — it is *not* part of a plan, so it isn't synced or exported, and it applies to every plan. **Making a column shown-by-default later needs a migration**, because every install's saved choice already lists it as hidden (the defaults are written by its first `save()`): bump `COLS_REV` and list the column in `COLS_REV_SHOWN[rev]`; `loadPrefs()` then unhides it **once** for anyone whose stored `cols.rev` is older (revision 1 = WBS). A column hidden again afterwards stays hidden, since the stored revision is then current. `loadPrefs()` is forgiving: unknown ids are dropped, Task Name is never hidden, and a column the saved prefs don't know yet (added by a later version) is appended and follows its own `dflt` — so shipping a new optional column never changes what an existing user sees. Because the menu re-renders on every click, the outside-click handler checks `e.target.isConnected` (same trap as the filter panel).

**Editing**: click a Resource cell (any task, groups included) for a text editor, an Actual Start/Finish cell (not groups) for a native date editor — blank clears it. WBS, Remaining Duration and Status are computed, so they have no editor. All three stored fields are in `syncPayload()`, so they are exported, backed up, synced to the plan's file and merged by the normal last-write-wins on `updatedAt`. All seven new columns are filterable (`FILTER_COLS`: WBS/Resource text, Actual Start/Finish date, Remaining number, Status list ordered Late → On Schedule → Future Task → Complete via `STATUS_ORDER`).

### Column filters

Excel-style filters on every data column, an explicit user request (first Start/Finish — "similar like if I filter a date column in Excel" — then "also good filters for the other columns"). A funnel button sits in each header in both views (`colHeadHtml()`; the compact Gantt list has the four columns it shows) and opens `#filterMenu`. The panel is **type-driven**: `FILTER_COLS` gives each column a `kind`, and the kind picks the rule set (`rulesFor(kind)`) and the list:

| column | kind | rules | list |
|---|---|---|---|
| Start, Finish | `date` | `DATE_RULES`: Equals / Before / After / Between, and Today, Tomorrow, Yesterday, This/Next/Last week, month, quarter, year, Year to date | Year › Month › Day tree |
| Task Name, Predecessors | `text` | `TEXT_RULES`: Equals, Does not equal, Begins with, Ends with, Contains, Does not contain (case-insensitive) | flat, sorted (natural order) |
| Duration, % | `number` | `NUMBER_RULES`: =, ≠, >, ≥, <, ≤, Between (either order) | flat, sorted numerically |
| Task Mode | `list` | none | the two modes |

Every list has a search box, `(Select All)` and — when some task has no value — `(Blanks)`. OK / Cancel, and "Clear filter" at the top.

- **State** (`colFilters`, one slot per `FILTER_COLS` key, made by `newColFilters()`) is *view state, like the selection*: in memory only — not in the plan data, not synced, gone on reload, and cleared by `resetTransientUI()` when the plan is switched. A `spec` is `{ type: 'rule', rule, a, b }` or `{ type: 'values', values: Set, blanks }`. The panel edits a **draft** (`filterDraft`); nothing applies until OK, and a selection that is "everything" applies no filter.
- **Evaluation** (`filterColValue`, `specMatches`, `ruleRange`): rows are filtered by what they *display* — dates via `effectiveDates()` (a summary uses its roll-up), Duration and % exactly as the grid cells compute them, Predecessors via `predecessorLabel()` (the very string the column shows, shared with `renderGrid()`). A task with no real value — a manual task with a free-text "TBD" date or duration, no predecessors — is a **blank**. As in Excel, a *positive* rule never matches a blank (date rules, text Equals/Contains/Begins/Ends, number =,>,<…), while the *negative* ones (Does not equal, Does not contain, number ≠) keep blanks; only `(Blanks)` in the list selects them on purpose. A task name can never be empty (`normalizeData` makes it "Untitled Task"), so Task Name has no `(Blanks)`. Weeks run Monday–Sunday like the calendar-week scale; relative rules are evaluated against today each render, so "this week" moves on by itself. All columns combine with **AND**, and each column's list is **cascaded**: it only offers values of tasks that every *other* column's filter lets through.
- **Hierarchy**: `filterShows(t)` = the task passes **or** any descendant shows, so a matching sub-task keeps its summary for context while non-matching siblings are hidden (memoised per render in `_filterShow`, cleared by `resetEffectiveCache()`). `visibleTaskList()` skips hidden tasks and — while any filter is on — ignores `collapsed`, so matches inside a collapsed group are visible; the chevron then shows "open" and `toggleCollapse()` just toasts ("Groups stay open while a filter is on") instead of changing anything. The stored `collapsed` flags are never touched, so clearing the filter restores the outline exactly.
- **Pinned rows** (`filterPinned`): a task you add (`addTask`), edit in the dialog (`saveTaskFromModal`) or inline (`commitInlineEdit`) stays visible even if it no longer matches — otherwise a new task (dated today) or an edited date would vanish under your cursor. Applying or clearing a filter empties the set.
- **Tree defaults** (an explicit user request): **years open, months collapsed** — opening the panel shows `2026 › September, October, …` and you open a month only to pick individual days; a whole month or year can be ticked without opening it, and a re-opened panel always starts from this default (`filterDraft.expanded` holds only the year keys). Search is the exception and shows whatever it needs. The expand arrows re-render the list, which detaches the clicked button *before* the document's outside-click handler runs — that handler therefore checks `e.target.isConnected`, or the panel would close on every expand/collapse.
- **Search** works like Excel's: typing selects exactly the matches (`(Select All Search Results)`), clearing it restores the previous selection; it matches the date as shown (`07.09.2026`), the month name and the year. Ticking a date while a rule is chosen switches the panel back to a list filter. **Escape in a `type=search` input clears it and fires an `input` event after our own Escape handler has closed the panel**, so the panel's event handlers all guard on `filterDraft` being null.
- **Feedback**: an active column's funnel is highlighted (tooltip: "Filtered: …"); `#filterBar` in the toolbar shows a chip per filter (× removes it), "N of M tasks" and "Clear all"; an empty result shows "No tasks match the filter" (list and chart) with a Clear button.
- **Layout**: the Duration and % columns were widened (96px / 54px) so their labels aren't cut off by the funnel. In the compact Gantt list the columns that don't exist there (Duration, %, Predecessors) have no button, but their filters still apply and keep their chip.
- Not built (deliberately, to keep it a *filter*): sorting from the header menu, and Excel's compound "Custom Filter… (and/or)". Between covers the common range case.

### Excel export

**Data → Export to Excel…** (an explicit user request: "well formatted") writes a real `.xlsx`, **hand-built with no library** — the app has no dependencies, and SheetJS's free build can't write styles anyway. An `.xlsx` is a ZIP of XML parts, so the module (`/* Excel export */`, before "Local backups") has four small pieces: `zipStore()` (a ZIP writer with CRC-32; entries are *stored*, not deflated — the files are small), `xlsxStyleBook()` (dedupes fonts/fills/borders/number formats into `styles.xml`; `style({...})` returns a cell-format index), `xlsxSharedStrings()`, and `xlsxSheet()` (rows/cells/merges/columns/data bar/print setup → worksheet XML). `buildXlsx({ scope, gantt })` assembles the package and returns a Blob; `downloadBlob()` saves it as `<plan name>-<date>.xlsx`. The dialog (`#excelModalBg`) offers **which tasks** — shown only when a column filter is on: all, or only those matching it (`exportTaskRows(scope)` uses `filterShows`) — and **Add a Gantt chart sheet**.

- **Tasks sheet**: title + subtitle rows, then **ID, then the task list's visible columns in the user's order** (the dialog's *Columns* choice: "As shown in the task list" — the default — or "All columns", in the default order; `XCOLS` maps each to a header and width, and the freeze pane, autofilter range and % data bar all follow the columns actually present) — the values the grid *displays* (same rules as `renderGrid()`: an automatic group shows its roll-up, a manual task its own dates, free-text "TBD" dates/durations are kept as text, `predecessorLabel()` for the references). Dates are **real Excel dates** (`xlsxSerial` = `dayNumber + 25569`, format `dd\.mm\.yyyy`), Duration a number with format `[=1]0" day";0" days"`, % a fraction with `0%` plus a **data bar**. The outline is exported in full, ignoring collapsed groups; indent = depth, groups bold on a light fill, milestones prefixed `◆`. Dark header row, thin light borders, a standard 19pt row height, **frozen panes** (header + everything up to Task Name), autofilter, landscape A4 fit-to-width, header row repeated on every printed page, page-number footer, coloured tab, gridlines off.
- **Gantt sheet** (skipped when nothing is scheduled): ID, indented name, Start, Finish, then **one column per ISO calendar week** (Monday–Sunday, like the app's Week scale) — months merged in the top header row, `CW n` rotated 90° below, this week's header highlighted amber; **solid = done, light = still to do, dark = group, ◆ = milestone**. A cell is solid when the bar's done portion (`Math.round(duration × progress / 100)` days) reaches into that week. Bar colours are the light theme's palette as hex (`XLSX_COLORS`, `statusColorHex()` mirrors `statusColorVar()` — complete/overdue/in-progress/not-started, or the task's own colour). Projects longer than 170 weeks switch to **one column per month** (year above, month name below).
- **Text is never a formula**: every string goes in as a shared string (`t="s"`), so a task called `=1+1` stays text. Cell text is cut at Excel's 32,767-character limit and control characters XML forbids are stripped (`xmlEsc`), or Excel refuses the file.
- **Excel is stricter than the tools available here.** It was verified by loading the files in openpyxl and by checks on the package itself (ZIP CRCs, well-formed XML, content types and relationships resolve, style/string indexes in range, rows and cells ascending, dimension and merge counts, worksheet elements in **schema order** — Excel rejects a misordered sheet that openpyxl accepts), but **not opened in Excel itself**. If Excel ever says it "found a problem with some content", the suspects are the worksheet element order, `styles.xml` counts, and the data-bar rule.

### Collapse all / Expand all (a multi-step cycle)

**One toggle button in the header cell of the ID column** (`#collapseToggleBtn`, `.id-toggle`) — directly above the first task, in both views (the Gantt side list has the same first column). It was two toolbar buttons first, then one collapse/expand toggle, and is now (by the user's request) a **cycle through the outline levels**: everything open → *collapse all* → open the **first level** of groups → the **next level** → … → everything open → around again. Level `L` means "groups nested fewer than `L` deep are open, deeper ones are closed", so `L = 0` is all collapsed and `L = levels` (the depth of the deepest group + 1) is all expanded. `collapseState()` works out which level the stored flags currently match (every depth below the deepest group contains a group, so each level is a distinct state), and `toggleAllCollapsed()` moves to `next`: `L + 1`, wrapping from fully open back to `0`. **A state the cycle can't produce** (one group opened or closed by hand) has `current === null` and the next click goes to *Collapse all*. Only groups are touched (`groupTasks()`); leaves keep their flag.

The icon and title show what the next click does: `angles-up` "Collapse all groups", then `angles-down` "Expand to level 1", "Expand to level 2", …, "Expand all groups" for the last step. The state is **derived from the stored `collapsed` flags**, so it survives a reload mid-cycle. Because `renderGrid()` rebuilds the header on every render, `updateCollapseButtons()` (called from `render()` after `renderGrid()`) re-applies icon, title and disabled state each time. Like the arrow on a single group (`toggleCollapse`) this is **view state and is deliberately not stamped with `updatedAt`** — a collapse must not travel to another device as if it were an edit. It is disabled when there are no groups, and **while a column filter is on**, because the filtered list shows every group open (see Column filters); the title says so, and calling `toggleAllCollapsed()` anyway just toasts.

### Drag-and-drop reordering, and Escape

Tasks are reordered by dragging **anywhere on the row** (the `.grid-row` itself is the `draggable` element — an explicit user request, after an earlier ID-cell-only handle), so clicks on cells, inline editing and double-click still work because a click that doesn't move never becomes a drag. The row shows the normal pointer at rest; the `grabbing` cursor only appears once the mouse has been held down on it for `GRAB_HOLD_MS` (250 ms) — `wireGrabCursor()` adds a `.grabbing` class after that delay and clears it on mouseup/dragstart. A plain CSS `:active` rule was deliberately not used: it flashes the grab cursor on every ordinary click, and a permanent `cursor: grab` made every row look like a drag handle. **The one exception is the row currently being edited**: `renderGrid()` renders it `draggable="false"`, because a draggable ancestor stops the mouse from selecting text inside an `<input>`; it turns draggable again on the next render after the edit. Clicking an editable cell (Start/Finish/Duration/Predecessors/Name) starts an inline edit and deliberately doesn't select the row (unchanged behaviour); every row is a drop target, in both Task view and Gantt view's label pane. The top half of a row means *insert before it*; the bottom half means *insert after it*, **except** that "after" an *expanded summary* is the slot directly beneath its header, i.e. its first sub-task (shaded `.drop-into`), since that's where the eye reads it. Dropping in the blank area below the last row moves the task to the end of the top level. The task takes the target's parent, so this both reorders and moves between groups; a summary always travels with its subtree (children reference it by `parentId`). A task can't be dropped onto itself or anywhere inside its own subtree (`canDropTaskOn()`) — that would create a `parentId` cycle.

Drop indicators (`.drop-before/-after/-into/-end`, `.dragging`) are classes toggled directly on the live row, **never a `render()`** — replacing the DOM mid-drag cancels the browser's drag. `moveTask(id, targetId, zone)` renumbers the destination level `0..n` (and the source level if the parent changed) and stamps `updatedAt` only on tasks whose `order`/`parentId` actually changed — `order` is a merged field, so an un-stamped renumber would never reach another device, and stamping everything would make untouched tasks look freshly edited. A drop that lands the task back where it started is a no-op (no save). Predecessor links are by internal id, so they survive a move; only the displayed `#` numbers (outline position) change.

**Escape** (the global handler in `wireGlobalEvents()`) closes any open dialog/menu first; only when none was open, and the key didn't come from a text field, does it clear `selectedTaskId`. It checks `e.target`, *not* `document.activeElement`: an inline editor's own Escape handler re-renders and destroys the focused input before the global handler runs, so `activeElement` is already `<body>` and would wrongly count as "not typing" — cancelling an edit used to deselect the row too. A related race: an inline editor only receives focus a frame after it appears, so an Escape in that instant lands on the page — the handler therefore also cancels any open inline edit itself (`if (!overlayOpen && editingCell) cancelInlineEdit()`) instead of clearing the selection and leaving the editor open. (This surfaced as an intermittent test failure: Playwright presses the key the moment the input exists.)

### Confirm dialog buttons

`openConfirmModal({ title, body, action, confirmLabel, confirmClass })` is shared by every confirmation. Its action button defaults to `btn btn-primary btn-danger`, which `.btn-primary.btn-danger` renders as a **filled red** button (white text, stays red on hover) — used by Delete task and Delete plan. A non-destructive caller passes `confirmClass`: Restore backup uses `btn btn-primary` (green — it replaces data after a safety download, but isn't a delete) and Disconnect file uses plain `btn` (an explicit request: no green button there). The default used to render green with red text, because `.btn-primary`'s background beat `.btn-danger`'s colour-only rule. ### Task constraints

`CONSTRAINT_TYPES` ports Microsoft Project's 8 primary constraint types (ASAP/ALAP/MSO/MFO/SNET/SNLT/FNET/FNLT), each entry carrying `hasDate`, `basis` (`'start'` or `'finish'` — which of the task's own dates the constraint date binds), and `bound` (`'lower'`, `'upper'`, or `'exact'`). A task stores `constraintType` (default `'ASAP'`) and `constraintDate` (`null` unless `hasDate`).

How each `bound` interacts with the forward-only cascade above is the crux of this port, since Milestone has no bidirectional scheduler to fully enforce an upper bound or a true backward ALAP pass:

- **`lower`** (SNET/FNET) and **`exact`** (MSO/MFO) fold directly into `constraintStart(task)` as one more candidate alongside every predecessor's own earliest-start push — whichever candidate is latest wins, the same mechanism that already resolves multiple predecessors against each other. This is why an MSO/SNET date can still end up pushed later than the pin: a predecessor genuinely demanding a later start always wins, exactly like real MS Project's own "meet as many constraints as possible" behavior when a schedule is over-constrained.
- **`exact`** additionally gets pinned immediately in `saveTaskFromModal()` the moment the constraint is set (the task's stored dates are set to the constraint date right then, preserving duration) — this is what makes "Must Start/Finish On" actually *move* a task instead of merely capping it, the one behavior `constraintStart()`'s lower-bound treatment alone wouldn't produce.
- **`upper`** (SNLT/FNLT) is deliberately **not** enforced by the cascade at all — this app's scheduling engine only ever pushes a date later (see `cascadeSchedule()`'s own comment above), so there is no code path that could honor an upper bound without contradicting that rule. Instead, `constraintViolated(task)` checks whether the task's *current* dates still satisfy its constraint (exact: date must match exactly; upper: current date must not exceed it) and the grid surfaces a mismatch via a small calendar icon next to the task name, turning `--danger`-colored when violated — the same "surface it, don't silently override a deliberate placement" stance already established for a manual placement ahead of a predecessor. Real MS Project does the same thing here: an over-constrained schedule gets a conflict indicator, not a silent reversal of whichever constraint lost.
- **ALAP** is treated identically to ASAP for actual date computation in this version — both are lower-bounded only by predecessors, with no backward slack-filling pass. A true ALAP (schedule as late as possible without delaying a successor) would need the same latest-start machinery `computeCriticalPath()` already computes for leaf tasks, just applied continuously rather than only behind the critical-path toggle; deferred as a genuine v1 scope cut rather than built halfway. No violation warning is shown for ALAP since there's nothing here to violate yet.

### Gantt rendering

Position math is plain day-number arithmetic (`dayNumber()`/`dayNumberToIso()`, UTC-based via `Date.UTC()`) rather than local-time `Date` arithmetic — the same reasoning Pulse's own Dashboard Gantt chart uses: two devices in different timezones must compute the identical pixel position from the same ISO date string, which a local-time parse doesn't reliably guarantee across a DST boundary. Display-facing formatting (`fmtDate()`/`fmtDateY()`) still parses as local time, matching how every other date renders in this app. `fmtDate()` (used everywhere task/Gantt dates and the week-level Gantt ticks are shown) renders as fixed `DD.MM.YYYY` rather than a `toLocaleDateString()` locale format — an explicit user request to match a traditional planner's date style regardless of browser locale; `fmtDateY()` (About dialog only) is unchanged.

The grid pane (task table) and the Gantt pane share one implicit vertical scroll position: the grid's own row list is `overflow: hidden` (never user-scrollable directly) and its `scrollTop` is driven programmatically from the Gantt pane's real scroll container, with wheel events over the grid forwarded into the Gantt pane's scroll instead (`wireScrollSync()`). This works because CSS `overflow: hidden` still permits *programmatic* `scrollTop` — it only suppresses the scrollbar UI and user-initiated wheel/touch scrolling — so the two panes' rows stay pixel-aligned with only one real scrollable element.

**In Gantt view, the grid pane is deliberately a compact label sidebar (ID/Name/Start/End only), not Task view's full spreadsheet** — `renderGrid()`'s `full` flag (`currentView === 'tasks'`) decides which cells actually get built (the CSS column templates for the two views already differ: the base `.grid-header`/`.grid-row` rule is the 4-column compact one, `.main.view-tasks` overrides it to the full 8-column one), so the two views never share a template with mismatched cell counts. Its width is a resizable, per-device preference (`gridPaneWidth`, default 360px, clamped to `[240, 720]`) — `#gridResizeHandle` (a thin drag strip pinned to the pane's right edge, only active in Gantt view — see `.main.view-tasks .grid-resize-handle`) drives it live via a CSS custom property (`--grid-pane-width`) during the drag and persists on mouseup, the same "update live, commit once" shape the Gantt bar drag handlers already use. Task view ignores the variable entirely (`width: auto; flex: 1`), since its pane is always meant to fill the screen.

Bar color (`statusColorVar()`) is either the task's own explicit `color` override, or derived from status: complete (100%) → `--status-complete`, overdue (end date in the past, not complete) → `--danger`, in-progress (progress > 0) → `--accent`, otherwise `--status-not-started`. A bar's unfilled portion is `color-mix(in srgb, var(--bar-color) 22%, var(--panel))` and its progress fill is the solid color — this is why the fixed palette only needs one solid hex per token rather than Pulse's paired solid/`-bg` tokens.

**Timescale** (`ZOOMS`: Week 14 px/day, Month 5, Year 1.5; the tabs in the top bar are generated from it). **Year is the default** (`DEFAULT_ZOOM`, an explicit user request), and the **Day scale was removed** at the user's request (a saved `'day'` falls back to Year). Every header tick spans its whole period — `renderGanttHeaderTicks()` returns `{ left, width, html|label, title, … }` and `renderGantt()` clips a tick that begins before the chart (the week/month/quarter holding the first day) to the left edge; `.gantt-tick` is `overflow: hidden` so a label is truncated, never spilled into the next tick. Ticks carry a `zoom-<id>` class. The header is always one row (`--row-h`) tall.

- **Saved scale and the one-time reset**: `prefsPayload()` stores `zoomRev: ZOOM_DEFAULT_REV` next to `zoom`, and `loadPrefs()` only honours a saved zoom whose `zoomRev` matches — otherwise it uses `DEFAULT_ZOOM`. This is deliberate: the previous default (Week) had been written to every install's prefs by its very first `save()`, so a plain change of the default would never have been seen by anyone who'd already opened the app. Bump `ZOOM_DEFAULT_REV` to reset everybody's scale once again; a scale chosen afterwards is remembered as usual.
- **Week**: **calendar weeks** (an explicit user request; the scale used to be labelled with each Monday's date). One tick per ISO 8601 week — weeks start on Monday, week 1 holds the year's first Thursday — labelled `CW 37` over the Monday's date (`07.09.`; the full `04.01.2027` on the first tick and wherever the year changes), with a tooltip giving the whole week (`CW 37: 07.09.2026 – 13.09.2026`). `isoWeekOf(dayNumber)` does the arithmetic on UTC day numbers (day 0, 1970-01-01, was a Thursday) and returns `{ week, year, monday }`; note the week's year can differ from its Monday's year (29.12.2025 is CW 1 of 2026). The prefix is the constant `CAL_WEEK_LABEL` (`'CW'`; German users may prefer `'KW'`).
- **Month**: one tick per month, `Sep 2026`, as wide as the month has days.
- **Year** (added by request): one tick per **quarter** — the year in bold on each Q1 (and on the first tick), `Q1`–`Q4` below it, a heavier left border (`.year-start`) at each year boundary. At 1.5 px/day a quarter is ~137px. Bars keep their 6px minimum width, and dragging/resizing rounds to whole days (`Math.round(dx / px)`), so 30px is 20 days.
- **Dependency arrows** used to be drawn one header-height (32px) too high, from the very first version: the `<svg>` overlay was `top: 0` of `.gantt-content`, but its y-axis (`barGeom`, the link-drag preview's `- ROW_H`) starts at the first row, i.e. below the sticky header. It is now `top: var(--row-h)`.

Dependency arrows are a single `<svg>` overlay (`#ganttDeps`) redrawn each render, one elbow-routed `<path>` per predecessor link between two currently-visible tasks (a link to/from a task hidden behind a collapsed ancestor is simply not drawn). Drag-to-link (the small circle handle on a bar's right edge) draws a temporary dashed preview path during the drag and resolves the drop target via `document.elementFromPoint()` against `data-row-id`/`data-id` attributes on the row background and bar elements.

### Fixed color palette (GitHub, dark-first)

Milestone originally ported Pulse's full switchable theme system — a light/dark toggle crossed with 5 color schemes (Standard, Modern/VS Code, Dracula/Alucard, GitHub, GitHub Dark Dimmed), each its own `[data-theme]`/`[data-scheme]` CSS block plus a palette-picker dropdown and `THEME_SCHEMES` array driving it. The 5-scheme picker was removed by explicit request in favor of always looking like GitHub — no `data-scheme` attribute, no picker UI, no `THEME_SCHEMES` array. The plain light/dark toggle came back afterward (also by request): `:root` is GitHub's Dark Dimmed palette (the default — `theme` starts `'dark'`, matching the "GitHub Dimmed by default" request), and `html[data-theme="light"]` overrides it with GitHub's own light palette — the inverse of the usual "light is `:root`, dark is the override" pattern, since dark is what's meant to be seen first here. `toggleTheme()`/`applyTheme()`/`updateThemeToggleUI()` are otherwise the same shape Pulse's own toggle uses. `.btn-primary` uses `--task-green` instead of `--accent` in both modes, matching GitHub's actual green primary-button convention (previously a github/githubdimmed-only override, now just the default regardless of light/dark).

### Native controls follow the theme (`color-scheme`)

`:root` sets `color-scheme: light` and `html[data-theme="dark"]` sets `color-scheme: dark`. That property is what tells the browser how to draw **its own** controls: the date picker's calendar icon *and* its popup, `<select>` menus, checkboxes, number spinners and scrollbars. Without it they are always drawn for a light page — the calendar icon in every date field was **black on the dark theme** (measured: contrast ≈ 39/255; ≈ 216 now). It is deliberately global rather than only on `input[type=date]`, so every date field is covered (task dialog, constraint date, actual dates, the inline list editor, the filter panel's date rules). `verify_dark_controls.py`-style checks screenshot a date field and measure the icon's ink against the field's background, since the native popup itself can't be captured headlessly.

### Top bar matches Pulse (and nothing else does)

By explicit user request the **top bar only** follows Pulse's look — a broader restyle of the whole app was tried and reverted because only the bar was wanted. It uses Pulse's values (read from `../Pulse/pulse.html`): `gap: 14px; padding: 0 16px`, brand `21px / 700 / -0.02em` with a 26px logo, the plan switcher (`.plan-btn`: the plan name, borderless and dim, background only on hover/open; 243px wide — the old name field's 182px + one third, at the user's request), `.topbar-divider` hairlines between the clusters, bordered pill `.view-tabs` with accent-coloured active text, bordered square `.icon-btn`s, and semibold `.btn`s at the browser's own 13.33px. **Every control rule is scoped to `.topbar`** (`.topbar .view-tab`, `.topbar .icon-btn`, `.topbar .btn`) precisely so the toolbar, list, dialogs and dropdowns keep their existing look — don't move these to the global `.icon-btn`/`.btn`/`.view-tab` rules. The second bar, the grid, and the modals are deliberately *not* Pulse-styled.

### Data durability

Same shape as Pulse/mytasks, sized down for a single-entity (`tasks`, not items+milestones+workstreams) data model:

- **Tombstones**: `deletedTaskIds` (`{id, deletedAt}[]`). `deleteTaskFlow()` cascades to the full descendant subtree, tombstones every id, and its undo toast restores the whole subtree *and* any predecessor links that were stripped from surviving tasks pointing at the deleted set (captured before the strip, replayed on undo) — a plain "restore the deleted tasks" undo without this would silently leave a surviving task's dependency broken even after the delete itself was undone.
- **Merge** (`mergeData(data, opts)`): flat, single-entity last-write-wins by `task.updatedAt`, tombstone-aware (respecting `opts.respectTombstones`, defaulting true — `applyImport('merge')` and a linked-file read both use the default; `applyImport('replace')`/backup restore skip merge entirely and overwrite). No per-field merge is needed the way Pulse's milestones-within-an-item needed one — a Milestone task has no nested sub-collection of its own.
- **Local backups**: one rolling snapshot per calendar day *per plan* in `localStorage["milestone-backups-<planId>"]`, capped at 7, via `maybeSnapshotBackup()` called from every `save()`. Restoring a backup restores into the current plan.
- **File System Access API sync**: one file *per plan* (not Pulse's later folder/multi-file split — that split exists specifically for *concurrent multi-workstream* editing, which doesn't apply to a single-project plan). `linkNewFile()`/`linkExistingFile()` pick a `FileSystemFileHandle` via `showSaveFilePicker()`/`showOpenFilePicker({ mode: 'readwrite' })` (without `mode` a picked file only has read permission), persisted across reloads in IndexedDB (`milestone-fs`, key `plan:<id>`). Only the **current** plan is in memory, so the sync globals (`syncFileHandle`, `fileSyncStatus`, `lastSyncedSnapshot`, the poll timer) describe the current plan's file and are re-pointed on every plan switch (`activatePlanFile()`). Writes are queued (`queueFileSyncWrite()`/`fileSyncWriteInFlight`/`fileSyncWritePending`) so a burst of rapid saves collapses to the minimum necessary writes and always reflects the latest state, not a stale queued snapshot — same mechanism Pulse's own file sync uses. Background polling every 45s (`FILE_SYNC_POLL_MS`) picks up changes made by another device sharing the same file (e.g. via iCloud Drive/OneDrive/Dropbox). Linking is **mandatory** wherever the browser supports it — see "Mandatory file linking" under Plans.

### Plans

A plan is one project: its own tasks, tombstones, backups and linked file. The current plan is the only one loaded (`project`/`tasks`/`deletedTaskIds` globals are always "the current plan"); everything else about the app is unchanged. The switcher is the button at the top left (`#planMenuBtn`, replaces the old project-name input): a menu listing the plans — each with its file name or "Browser only" — plus New plan, Open file as plan, Rename, Duplicate and Delete (all acting on the current plan). New/Rename share one small dialog (`#planModalBg`); "Create with file…" opens the save picker *first*, straight from the click (it needs the user gesture), and only then creates the plan and writes its first content into the file.

**Migration** (`initPlans()`): the first time this build runs, the single pre-plans project (`milestone-v1`) becomes plan id `plan1` — copied, not moved, so the old keys are a rollback copy and, once `milestone-plans` exists, are never read again. Its theme/zoom/view/pane width seed `milestone-prefs`, its `milestone-backups` are copied to `milestone-backups-plan1`, and `_fsMigrateLegacyKey()` copies the old IndexedDB handle (`syncFile`) to `plan:plan1` exactly once (guarded by `milestone-handle-migrated`, otherwise unlinking Plan 1 would bring the file back on the next load).

**Switching** (`switchPlan(id)`), in this order: `persistLocal()` (browser copy, synchronous) → `flushFileSync()` (let the in-flight write land, then write once more) → `planEpoch++` → stop polling → load the other plan → `resetTransientUI()` (selection, inline edit, task dialog, and **any Undo toast** — an Undo for the old plan must not act on the new one) → `render()` → `activatePlanFile(true)`. The `true` matters: a switch is a click, so a linked file whose permission lapsed can be re-requested right there instead of falling back to the amber Reconnect button (a plain page load has no gesture and still shows Reconnect).

**The write race, and why `planEpoch` exists.** File I/O is async, so a write or a poll for plan A can still be in flight after the user has switched to B. `writeSyncFile()` therefore captures *both* the file handle and the payload text synchronously, before its first `await` — an in-flight write always puts A's data into A's file, never B's — and every async sync function (`writeSyncFile`, `pollFileSync`, `reconnectFile`, `finishLinking`, `activatePlanFile`) compares `planEpoch` after each `await` and drops its result if the plan changed. Without that, a poll that was waiting on A's file would `mergeData()` A's tasks into B. The Playwright tests cover both (edit + switch in the same tick, and a deliberately slow `getFile()`).

**One file, one plan.** Two plans on the same file would overwrite each other's changes, so linking refuses a file another plan already uses (`findPlanForHandle()`, via `handle.isSameEntry()`), and "Open file as plan" on a file that's already a plan switches to that plan instead of adding a second one. The plan↔file association is local to each device and deliberately **not** stored inside the file: copy a file in Finder and an embedded plan id would make two files claim to be the same plan.

**Deleting** removes the plan from *this browser only* — its data, backups and file handle; the file itself is never touched, and the confirm dialog says so. The removed plan is kept in the Undo toast's closure for its 6 seconds. The last remaining plan can't be deleted (the menu item is disabled). `updatePlansIndex(fn)` is always a read-modify-write against `localStorage`, never an in-memory copy, so a second tab that added or renamed a plan isn't clobbered.

The test harness used for this drives real Chromium with `showSaveFilePicker`/`showOpenFilePicker` replaced by functions that return **OPFS** file handles (`navigator.storage.getDirectory()`): those are genuine `FileSystemFileHandle`s (they have `createWritable`, `queryPermission`, `isSameEntry` and can be stored in IndexedDB), which is the only way to exercise the sync code headlessly.

### Mandatory file linking

Every plan must be linked to a file (an explicit user request; before it, linking was optional and a plan could live only in the browser). A plan can never be *left* without a file, but it can be **disconnected and reconnected** (an explicit user request, so a wrong or moved file can be swapped for a new or different one) — see "Disconnecting" below. What enforces it:

- **`fileLinkRequired()`** = the browser supports files **and** `fileSyncStatus` is `'unlinked'` or `'missing'`. `enforceFileLink()` runs at the end of `activatePlanFile()` — i.e. on page load and after every plan switch — and opens `#fileSyncModalBg` when that holds. This one dialog covers first run, the migrated Plan 1 of an existing install (no file yet), a plan whose file link is gone, and a missing file.
- **The dialog can't be dismissed**: no × and no "Not now", the backdrop ignores clicks, and Escape leaves it alone (the Escape handler counts it as an open overlay but never closes it). Cancelling a file picker just leaves it up. It is *always* in this state — there is no closable variant, because a plan can only be unlinked while that dialog is about to open. It offers **Create new file** (the plan's current tasks are written into it) and **Open existing file** (merged into the plan, or replacing it if the plan is still empty).
- **New plan** and **Duplicate** go through `createLinkedPlan(name, data)`: the save picker opens *first*, straight from the click (needs the user gesture); only after a file is chosen is the plan created, written into the file and opened, so a plan is never in an unlinked state and cancelling creates nothing. The plan dialog's button reads "Create…" (a file dialog follows). `refuseIfFileBelongsToAnotherPlan(handle, true)` also rejects the *current* plan's file here — a new plan reusing it would overwrite it.
- **Missing file** (`fileSyncStatus === 'missing'`): `pollFileSync()` gets `NotFoundError` from `getFile()` → `markFileMissing()` stops polling, shows "File missing" on the button and re-opens the dialog (title "Linked file not found"). Only the *read* detects this: a *write* to a deleted file silently re-creates it at the same path (verified in Chromium, `createWritable()` + `close()` both succeed), so nothing is lost — the dialog is for a file that was moved or renamed.
- **Browsers without the File System Access API** (Safari, Firefox): there is no way to write a file, so requiring one would lock the app out. `fileSyncStatus` is `'unsupported'`, the file button is hidden, no dialog appears, and plans stay browser-only (New plan/Duplicate create them directly). `fileLinkRequired()` is false there.
- **Disconnecting**: the linked file button (top right) and the plan menu's "Disconnect file…" both call `disconnectFile()`, which asks for confirmation and then runs `unlinkFile()`: `flushFileSync()` first (so the file holds everything up to the last edit — an edit made just before disconnecting still lands in it), then `planEpoch++`, clear the handle/snapshot/polling, delete the `plan:<id>` handle from IndexedDB, clear `fileName` in the index — and finally `enforceFileLink()`, so the mandatory dialog opens **immediately** (an explicit user request: "force linking a file after disconnect"). The old file is never deleted or touched again. From the dialog the user can create a **new** file (the plan's tasks are written into it), open a **different** existing file (its tasks are *merged* into the plan — nothing is dropped, and the merged result is written to that file), or pick the very same file again. The "Disconnect file…" item is disabled when the plan has no file and absent in browsers without file support.
- **Tests**: with the API present the link dialog blocks the page, so older headless scripts that don't care about files disable it (`delete window.showOpenFilePicker`) and run in the browser-only fallback.

### PWA

`manifest.json` + `sw.js` (cache-first app shell with network-first navigation, same shape as Pulse's own service worker) + `icons/` (`icon.svg` source plus `icon-180/192/512.png`). **The logo is a solid diamond (the standard Gantt milestone symbol) with three staggered Gantt bars cut out of it — deliberately not on a circle, an explicit user request, and chosen over four other candidates for staying legible at the top bar's 26px.** It appears in three places that must change together: the top-bar `.brand` SVG, the About dialog SVG (both inline, `fill="currentColor"` so they follow the theme, each with its **own unique `<mask id>`** — two inline SVGs sharing a mask id makes the second one render blank/wrong), and `icons/icon.svg`. The icon is a *full-bleed* accent (`#0969da`) square with the white mark at 70% scale — no rounded corners, since iOS and Android apply their own mask and a pre-rounded tile would show a dark/white corner; the mark sits inside the maskable safe zone. The PNGs are rendered from `icon.svg` with headless Chromium (screenshot an `<svg>` sized to each target; no SVG rasterizer is installed), e.g. via Playwright `page.set_content(svg)` + `page.screenshot(clip=...)`. Bump `CACHE_NAME` in `sw.js` when the icon changes so installed copies refresh it. `start-milestone.command`/`stop-milestone.command` mirror Pulse's own local-server launch scripts, on port 8937 (Pulse's own is 8936 — kept distinct so both apps' dev servers can run at once).

## Known v1 limitations

- Critical path slack treats every dependency as Finish-to-Start (see "Scheduling engine" above).
- Auto Scheduled tasks are still push-later-only: unlike MS Project, moving a predecessor (or recording an early actual start/finish) *earlier* doesn't pull an Auto successor earlier (only switching a task to Auto does — see Task Mode). There is no baseline: Start/Finish are the plan and are never overwritten by actual dates (a possible future addition would be an optional "Set baseline" snapshot).
- ALAP behaves identically to ASAP — no backward slack-filling pass yet (see "Task constraints" above).
- SNLT/FNLT (Start/Finish No Later Than) are flagged when violated, never enforced — this app's cascade is forward-push-only.
- Two browser tabs on the *same* plan still race each other (last write to `localStorage` wins; a linked file's 45s poll merges) — plans didn't change that. Two tabs on *different* plans are fine.
- No automated test suite yet.
- No RBAC/roles, no daily-backup-to-a-linked-folder, no multi-file sync split — all deliberately out of scope for a single-user, single-project local planner (unlike Pulse, which is a multi-role team dashboard).
